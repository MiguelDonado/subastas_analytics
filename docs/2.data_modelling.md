# Data modelling

Decisions about which data goes into the pipeline, and why.

**Where to place a decision:** in the layer where it takes effect, even if it mentions other layers. Each decision has its own `###` heading.

## Overview

### Medallion architecture

The data goes through three layers, each with its own PostgreSQL schema:

| Layer | What it holds | How it's loaded |
|---|---|---|
| **Bronze** | Raw announcements from the BOE API | Only the announcements from the past 7 days |
| **Silver** | Cleaned data, enriched with Claude and Goolzoom, in 3NF, plus the rejected announcements in their own table | Only the announcements that aren't in silver yet and weren't rejected |
| **Gold** | Star schema, plus a bridge table between lots and catastral references, and the view `gold.app_lots` that the app reads | Fully reloaded from silver on every run: `TRUNCATE` and insert |

Each layer was built step by step. Every step was executed to check its data, and that data then helped with modelling the next layer. Gold was also shaped from the other direction, by what the app needs. Real projects usually combine both approaches too: the data shows what's possible, and its final use shows what's needed.

### Only automatic indexes are used

PostgreSQL automatically creates an index for every `PRIMARY KEY` and `UNIQUE` constraint, but not for foreign keys. No other indexes are created. An index on a foreign key helps to find a few child rows, in a join or when a parent row is deleted, but here gold is rebuilt by reading whole tables, parent rows aren't deleted and the tables are small.

## Bronze

### Subsequent auctions are new announcements

Each subsequent auction of a lot (2nd, 3rd or later) is published in the BOE summary as a new announcement, with a different `boe_ref`. So the pipeline loads it like any other announcement.

### Only the BOE's content is stored in bronze

Claude and Goolzoom can only be called with data that is already in bronze, so their results are enrichment, not a source, and they go straight to silver:

- **Claude:** its response is never raw, because it follows a schema I give it.
- **Goolzoom:** its response is raw, and Python parses it to keep only the fields needed. It could be stored, but it's dropped for the same reason: it's enrichment.

Rebuilding silver would mean paying for those calls again, and the results may differ. That isn't a problem, because silver doesn't need rebuilding: each run only loads from bronze the announcements that aren't in silver yet.

### Auction PDFs are not stored

The pipeline doesn't download any PDF. There are two types related to an auction:

| PDF | Where it is |
|---|---|
| **BOE announcement** | Linked from each announcement (`url_pdf`). Its text is already stored in `announcement_text`. |
| **Pliego de condiciones** | Only on the Hacienda website. The BOE data mentions it in the text, but gives no URL. |

The Shiny app is for exploring auctions and marking the properties I'm interested in, and that only needs the data extracted from the announcement text. The PDFs are only needed at the very end, just before purchasing, and only for the few properties I've marked. At that point, opening them by hand is enough.

## Silver

### Rejected announcements have their own table

An announcement with no held date or no valid lots is rejected, so it isn't stored in `silver.auctions`. Without a record of it, it would stay pending and be sent to Claude again on every run, so its `boe_ref` and the reason go in `silver.rejected_announcements`.

A separate table is preferred to a status column in `silver.auctions`, such as `is_rejected`:

- **`held_date` stays `NOT NULL`:** a rejected announcement may have no date, so a column would mean making `held_date` nullable, and the database would no longer guarantee that every auction has one.
- **No filter to forget:** with a column, every query on `silver.auctions`, including the gold load, would have to exclude rejected rows. If one forgot, they would reach gold with no error.
- **Clear meaning:** `silver.auctions` only holds valid auctions.

The separate table only costs one extra join in the pending query. Nothing else is lost, because the announcement's text and publication date are still in `bronze.auctions`, joined by `boe_ref`.

This is a common approach, usually called a **quarantine** or **rejects table**, and it's standalone for the same reason as here: rejected rows don't meet the rules of the main tables, so foreign keys to them wouldn't fit. It keeps bad data out of the clean tables without losing track of it. 

It also allows reprocessing. Teams usually analyse the rejected rows to find out why they failed, fix the cause (for example, a bug in the extraction or a rule that's too strict), and send those rows through the pipeline again. Here, that means deleting a row from `silver.rejected_announcements`, which makes that announcement pending again on the next run.

## Gold

### A lot keeps the same catastral references in every auction

A lot contains the same catastral references regardless of the auction (1st, 2nd, 3rd or later), as long as it hasn't been sold. So the same list of references means the same property, and `gold.app_lots` uses that list to find each lot's earlier auctions and set `is_latest`.

### The announcement URL is only readable in the app

The URL downloaded from the BOE opens raw XML, which is hard to read. The app needs a readable page instead, and it's the same URL with `xml` changed to `txt`:

| Where | Column | Value |
|---|---|---|
| `bronze.auctions` | `source_url` | XML link, unchanged |
| `silver.auctions` | `source_url` | XML link, unchanged |
| `gold.dim_auctions` | `source_url` | XML link, unchanged |
| `gold.app_lots` (view) | `announcement_url` | Readable link, renamed here |

The tables keep `source_url` because it records where the data was actually downloaded from. The readable link is only a display need of the app, so it's calculated in the view, and it has a different name because it's no longer where the data came from.
