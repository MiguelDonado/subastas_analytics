# Reviews

Users can write a note on each lot, e.g. "visited, the house needs a new roof" or "too far from the road". Each user has their own notes.

It's done in two steps:

1. **Now: a note per lot.**

## Where the data lives
The notes are entered by the users, while bronze, silver and gold are written by the pipeline and can be rebuilt. The notes can't be rebuilt, so they live in their own schema, `app`, created by `include/sql/create_app.sql`. That file isn't part of the DAG: it's run once by hand.

```
app.users       (user_id, username, password_hash, created_at)
app.lot_reviews (user_id, boe_ref, lot_number, notes, updated_at)
```

## One row per user and lot
The primary key of `app.lot_reviews` is `user_id` + `boe_ref` + `lot_number`: each user has at most one note per lot.

- **The lot is `boe_ref` + `lot_number`, not `lot_id`.** `lot_id` is generated automatically, so rebuilding silver gives every lot a new number and the notes would point to the wrong lots. 
- **No surrogate key** (like a `review_id`). A surrogate key helps when other tables point to this one, so their foreign keys need one column instead of three. No table points to `app.lot_reviews`, so it would be a column that nothing uses.

## A row only exists if the note has text
`notes` is `NOT NULL`, and the app never saves an empty note:

- **Write a note and save:** the row is created, or updated if it already exists.
- **Clear the note and save:** the row is deleted.

So a lot has either a row with a real note, or no row at all.

## Each user has their own notes
The app is used by a known group of people, so each one logs in and only sees their own notes.

- **Login with shinymanager:** a login screen in front of the app.
- **Users in Postgres (`app.users`), created by hand:** there's no sign-up, which is fine for a known group. Adding a person is one `INSERT`. shinymanager keeps its users in a local SQLite file by default, but on Posit Connect Cloud the app's files are replaced on every redeploy, so the users could be lost.
- **Only the hash of the password is stored** (see "Passwords" below).
- **The notes follow each person to any device**, because they're tied to the login, not to the browser.
- **Not in `gold.app_lots`:** the notes depend on who is logged in, so the app reads that user's notes and joins them to the lots in R.

## Passwords
**Creating a user:** you choose a password, e.g. `"pino2026"`, and `sodium::password_store("pino2026")` gives a hash, a long text like `$7$C6..../....abc...`. That text goes into `app.users.password_hash`. The password itself is never stored.

**Logging in:** `sodium::password_verify(stored_hash, typed_password)` returns `TRUE` or `FALSE`.

**The salt:** `password_store()` adds a random value, the salt, before hashing, so hashing the same password twice gives two different hashes. That's why the login can't just hash what was typed and compare the two texts. The stored hash contains its own salt and settings: `password_verify()` reads them, hashes the typed password with that same salt, and compares.

Why it's done this way:

- **The hash can't be turned back into the password.** If someone read `app.users`, they wouldn't see any password.
- **Two users with the same password get different hashes**, because of the salt. A leak doesn't show who shares a password, and ready-made tables of hashes of common passwords don't work.
- **The hashing is slow on purpose** (scrypt). A login only does it once, so it isn't noticed, but trying millions of passwords against a leaked hash would take a very long time.

## Login
How the login was added to the app:

1. **Install the packages** in `dashboard/`: `renv::install(c("shinymanager", "sodium"))`, then `renv::snapshot()` once the code uses them, so they're recorded in `renv.lock`.
2. **Write `dashboard/R/auth.R`** with `check_user(user, password)`, the function shinymanager uses to check each login. It looks up the user in `app.users` and checks the password with `sodium::password_verify()`.

   The name `check_user` isn't required: any name works, because the function is passed to shinymanager in the server. What shinymanager does require is that its input and output follow this format:
   - **Input:** the user and the password typed in the login screen.
   - **Output:** a list with two keys:
     - `result`: `TRUE` if the login is correct, `FALSE` if not.
     - `user_info`: only when `result` is `TRUE`, a list with what the app needs to know about the user, here `user` and `user_id`. The server reads them from `res_auth`, e.g. `res_auth$user_id`.
3. **Show shinymanager's login screen** in front of the app: `ui <- secure_app(ui, language = "es")`.
4. **Split the server in two:**
   - **`server`** runs shinymanager's login (`secure_server(check_credentials = check_user)`). After a correct login, shinymanager reloads the page with the app, and `res_auth$user_id` holds who logged in.
   - **`app_server`** is all the app's code: filters, table, map, markers. `server` starts it with an `observeEvent` on `res_auth$user_id`, which only runs once there's a `user_id`, and with `once = TRUE`, because it must only be started once. From then on the app works as before, and it gets the `user_id` to read and save that person's notes.

**Why the server is split:** without it, the whole server already runs on the login page, before anyone has logged in. Most of it does nothing harmful here, but running the app's code before the login, even if it does no harm, isn't right. With the split, nothing of the app runs until someone has logged in.

**Adding a user:** `subastas_app` can't write to `app.users`, so users are added as the pipeline's user:
1. Make the hash in R, without typing the password in the command, so it isn't saved in R's history: `sodium::password_store(rstudioapi::askForPassword("Contraseña"))`. It prints the hash, a long text that starts with `$7$`: copy it.
2. In DBeaver, as the pipeline's user, paste it in the `INSERT`: `INSERT INTO app.users (username, password_hash) VALUES ('<name>', '<hash>');`

## The database is the only source of the notes
The notes are never kept in R between actions: every time the app needs them, it reads them from `app.lot_reviews`, and every save writes there straight away. So what the app shows is always what's saved.

| When | What the app does with the database |
|---|---|
| "Buscar" | Reads the user's notes for the table |
| Selecting a row | Reads that lot's note for the box |
| "Guardar" | Saves the note, then reads the notes again for the "Nota" column |

It costs one small query each time, only the notes of one user, so it isn't noticed. In exchange there's no copy in R that could get out of date.

## Reading the notes
After the login, the app reads the notes of the person logged in and adds them to the lots:

1. **`read_user_notes(con, user_id)`** in `dashboard/R/db.R` reads that user's notes from `app.lot_reviews`: `boe_ref`, `lot_number` and `notes`, one row per lot with a note.
2. **They're read in `filtered_lots`**, the `eventReactive` that runs on every click on "Buscar". It opens a connection, reads the notes, closes it, and joins them to the lots with `left_join(notes, by = c("boe_ref", "lot_number"))` before the filters.

- **`left_join`:** lots without a note stay in the list, with `notes` empty (`NA`).
- **On every search, not once at login:** the notes are always what's in the database right now, so there's no copy in R to keep up to date. 
- **Inside `app_server`, not at the top of `app.R`:** the top of the file runs once for everyone, but the notes depend on who logged in (`user_id`).

## Saving a note
The note is written in the "Nota del lote" box of the sidebar and saved with "Guardar".

1. **`observeEvent(input$save_note, ...)`** runs every time "Guardar" is clicked.
2. **It takes the selected row's lot:** its `boe_ref` and `lot_number`, which identify the lot in `app.lot_reviews`.
3. **It calls `save_user_note(con, user_id, boe_ref, lot_number, notes)`** in `dashboard/R/db.R`, with the text of the box:
   - **With text:** the row is created, or updated if it already exists (`INSERT ... ON CONFLICT ... DO UPDATE`).
   - **Empty, or only spaces:** the row is deleted.
4. **It shows a short message**, "Nota guardada" or "Nota borrada", so you know it worked.

"Guardar" is disabled while no row is selected

## Nota column
The table shows each lot's note in the "Nota" column, and it's updated as soon as a note is saved.

**1. The table's data is built by a function, `table_data(df)`**, at the top of `app.R`. It takes `filtered_lots()` and returns the data frame given to `datatable()`: it prepares the columns (`mutate`) and keeps the ones shown (`select`). The table needs this in two places, when it's drawn and when it's updated after a save, and both must give the same columns in the same order.

- **Only the first 40 characters** of the note are shown (`str_trunc`), so a long note doesn't make its row very tall. The full note is in the box.
- **`htmlEscape`:** the table shows HTML, for the BOE link (`escape = FALSE`), so a note with `<` or `>` could display wrongly without it.
- **Lots without a note** show an empty cell, not `NA`.

**2. After saving, only the table's data is replaced, not the whole table.** Redrawing the table would lose the selected row and go back to page 1. Instead, `dataTableProxy("lots") |> replaceData(new_data, ...)` sends new data to the table already drawn:

- **`new_data`** is `filtered_lots()` with its `notes` column replaced: the old one is removed and the user's notes are read again from the database, which already has the note just saved. Then it goes through `table_data()`, like when the table is drawn.
- **`resetPaging = FALSE`** keeps the page, and **`clearSelection = "none"`** keeps the row selected. The map doesn't change either.
- **The rows stay in the same order**, so the selected row is still the same lot.

## Database users
These are the database users, not the app's users in `app.users`. There are two:

- **The pipeline's user:** Airflow connects with it, and it creates and owns every schema and table. Two files are involved, each with its own job:
  1. **`subastas-db.env` creates the user.** It isn't created in any SQL file: the `postgres:17` image reads `POSTGRES_USER`, `POSTGRES_PASSWORD` and `POSTGRES_DB` on its first start, when the volume is empty, and creates that user as a superuser, plus the database. On Neon, it's the owner role Neon creates with the project.
  2. **`.env` tells Airflow how to connect**, with `AIRFLOW_CONN_SUBASTAS_DB='postgresql://user:password@subastas-db:5432/subastas'`: which user and password, where the database is (`subastas-db`, the container's name on the Docker network) and which database. Airflow finds it by a naming convention:
     - Astro loads `.env` into the Airflow containers as environment variables.
     - The DAG's tasks only use the connection id: `conn_id="subastas_db"`.
     - Airflow looks for an environment variable called `AIRFLOW_CONN_` + the id in uppercase, `AIRFLOW_CONN_SUBASTAS_DB`, and connects with what's in it.

     That's why `AIRFLOW_CONN_SUBASTAS_DB` doesn't appear anywhere in the code: the code says `subastas_db`, and Airflow builds the name.

  The user and password in the URI have to be the same as in `subastas-db.env`, or the DAG can't connect.
- **`subastas_app`:** the app connects with it. It's the only user created explicitly, by `include/sql/create_app_role.sql`, and it can only do what the app needs:

| Schema | What `subastas_app` can do |
|---|---|
| `gold` | Read the tables and views |
| `app` | Read `app.users` for the login, and read and write `app.lot_reviews` |
| `bronze`, `silver` | Nothing |

### Why the app has its own user
It follows the principle of least privilege: each user gets only the rights it needs.

- **Data protection:** the app can't change bronze, silver or gold by mistake, e.g. through a bug.
- **Security:** if the app is ever compromised, the attacker only gets what `subastas_app` can do: read gold and write notes.
- **Separate responsibilities:** the pipeline manages the data, and the app reads it and manages the notes.
- **Maintainability:** new tables and views in gold already get `SELECT` for the app (`ALTER DEFAULT PRIVILEGES`), so they don't need another `GRANT`.

### How the app's user was created
Done once, by hand. None of it is part of the DAG. The `app` schema is created first, because the user gets permissions on it.

1. **Write the script for the schema and its tables:** `include/sql/create_app.sql` creates the `app` schema, `app.users` and `app.lot_reviews`.
2. **Write the script for the app's user:** `include/sql/create_app_role.sql` creates `subastas_app` and gives it its permissions. It has no password, so the password never reaches git.
3. **Run both scripts from DBeaver**, connected as the pipeline's user, `create_app.sql` first. As the pipeline's user because only the owner of the schemas can grant rights on them, and because `ALTER DEFAULT PRIVILEGES` only covers the tables and views that this same user creates in gold later. Run each one as a script (`Alt+X`): `Ctrl+Enter` only runs the statement under the cursor.
4. **Set the password of `subastas_app`** with the psql that comes inside the database container, so nothing has to be installed and the password isn't saved anywhere:
   ```bash
   docker exec -it <subastas-db container> psql -U <pipeline user> -d subastas
   ```
   and then `\password subastas_app`, which asks for it without showing it. The container's name is in `docker ps`.
5. **Check the permissions,** with a new DBeaver connection as `subastas_app`:
   ```sql
   SELECT count(*) FROM gold.app_lots;  -- works
   SELECT count(*) FROM silver.lots;    -- permission denied
   ```
6. **Point the app to the new user:** in `dashboard/.Renviron`, set `SUBASTAS_DB_USER` to `subastas_app` and `SUBASTAS_DB_PASSWORD` to its password.
