# Reviews

Users can write a note on each lot, e.g. "visited, the house needs a new roof" or "too far from the road". Each user has their own notes.

It's done in two steps:

1. **Now: a note per lot.**

## Where the data lives
The notes are entered by the users, while bronze, silver and gold are written by the pipeline and can be rebuilt. The notes can't be rebuilt, so they live in their own schema, `app`, created by `include/sql/create_app.sql`. That file isn't part of the DAG: it's run once by hand.

```
app.users       (user_id, username, password_hash, created_at)
app.lot_reviews (user_id, boe_ref, lot_number, notes, updated_at)
```

## One row per user and lot
The primary key of `app.lot_reviews` is `user_id` + `boe_ref` + `lot_number`: each user has at most one note per lot.

- **The lot is `boe_ref` + `lot_number`, not `lot_id`.** `lot_id` is generated automatically, so rebuilding silver gives every lot a new number and the notes would point to the wrong lots. 
- **No surrogate key** (like a `review_id`). A surrogate key helps when other tables point to this one, so their foreign keys need one column instead of three. No table points to `app.lot_reviews`, so it would be a column that nothing uses.

## A row only exists if the note has text
`notes` is `NOT NULL`, and the app never saves an empty note:

- **Write a note and save:** the row is created, or updated if it already exists.
- **Clear the note and save:** the row is deleted.

So a lot has either a row with a real note, or no row at all.

## Each user has their own notes
The app is used by a known group of people, so each one logs in and only sees their own notes.

- **Login with shinymanager:** a login screen in front of the app.
- **Users in Postgres (`app.users`), created by hand:** there's no sign-up, which is fine for a known group. Adding a person is one `INSERT`. shinymanager keeps its users in a local SQLite file by default, but on Posit Connect Cloud the app's files are replaced on every redeploy, so the users could be lost.
- **Only the hash of the password is stored** (see "Passwords" below).
- **The notes follow each person to any device**, because they're tied to the login, not to the browser.
- **Not in `gold.app_lots`:** the notes depend on who is logged in, so the app reads that user's notes and joins them to the lots in R.

## Passwords
**Creating a user:** you choose a password, e.g. `"pino2026"`, and `sodium::password_store("pino2026")` gives a hash, a long text like `$7$C6..../....abc...`. That text goes into `app.users.password_hash`. The password itself is never stored.

**Logging in:** `sodium::password_verify(stored_hash, typed_password)` returns `TRUE` or `FALSE`.

**The salt:** `password_store()` adds a random value, the salt, before hashing, so hashing the same password twice gives two different hashes. That's why the login can't just hash what was typed and compare the two texts. The stored hash contains its own salt and settings: `password_verify()` reads them, hashes the typed password with that same salt, and compares.

Why it's done this way:

- **The hash can't be turned back into the password.** If someone read `app.users`, they wouldn't see any password.
- **Two users with the same password get different hashes**, because of the salt. A leak doesn't show who shares a password, and ready-made tables of hashes of common passwords don't work.
- **The hashing is slow on purpose** (scrypt). A login only does it once, so it isn't noticed, but trying millions of passwords against a leaked hash would take a very long time.

## Database users
These are the database users, not the app's users in `app.users`. There are two:

- **The pipeline's user:** Airflow connects with it, and it creates and owns every schema and table. Two files are involved, each with its own job:
  1. **`subastas-db.env` creates the user.** It isn't created in any SQL file: the `postgres:17` image reads `POSTGRES_USER`, `POSTGRES_PASSWORD` and `POSTGRES_DB` on its first start, when the volume is empty, and creates that user as a superuser, plus the database. On Neon, it's the owner role Neon creates with the project.
  2. **`.env` tells Airflow how to connect**, with `AIRFLOW_CONN_SUBASTAS_DB='postgresql://user:password@subastas-db:5432/subastas'`: which user and password, where the database is (`subastas-db`, the container's name on the Docker network) and which database. Airflow finds it by a naming convention:
     - Astro loads `.env` into the Airflow containers as environment variables.
     - The DAG's tasks only use the connection id: `conn_id="subastas_db"`.
     - Airflow looks for an environment variable called `AIRFLOW_CONN_` + the id in uppercase, `AIRFLOW_CONN_SUBASTAS_DB`, and connects with what's in it.

     That's why `AIRFLOW_CONN_SUBASTAS_DB` doesn't appear anywhere in the code: the code says `subastas_db`, and Airflow builds the name.

  The user and password in the URI have to be the same as in `subastas-db.env`, or the DAG can't connect.
- **`subastas_app`:** the app connects with it. It's the only user created explicitly, by `include/sql/create_app_role.sql`, and it can only do what the app needs:

| Schema | What `subastas_app` can do |
|---|---|
| `gold` | Read the tables and views |
| `app` | Read `app.users` for the login, and read and write `app.lot_reviews` |
| `bronze`, `silver` | Nothing |

### Why the app has its own user
It follows the principle of least privilege: each user gets only the rights it needs.

- **Data protection:** the app can't change bronze, silver or gold by mistake, e.g. through a bug.
- **Security:** if the app is ever compromised, the attacker only gets what `subastas_app` can do: read gold and write notes.
- **Separate responsibilities:** the pipeline manages the data, and the app reads it and manages the notes.
- **Maintainability:** new tables and views in gold already get `SELECT` for the app (`ALTER DEFAULT PRIVILEGES`), so they don't need another `GRANT`.

`create_app_role.sql` is run once by hand, as the pipeline's user, after `create_app.sql`:

- **As the pipeline's user,** because only the owner of the schemas can grant rights on them. Also, `ALTER DEFAULT PRIVILEGES` gives `SELECT` on the tables and views that this same user creates in gold later, so the views the DAG recreates don't need another `GRANT`.
- **The password isn't in the file,** so it never reaches git. It's set by hand right after, in psql: `\password subastas_app`. Then it goes in `SUBASTAS_DB_USER` and `SUBASTAS_DB_PASSWORD` of `dashboard/.Renviron` (and in Connect Cloud's settings).
