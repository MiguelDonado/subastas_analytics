# Failure modes

Every decision point in the pipeline, one row each, so it's possible to check that every case is covered. Each row has an id (`B1`, `S1`, `G1`...) so a test can point to the row it proves.

This table was built by reading the code, not by running it. No row has a test yet.

**Status:**
- ✅ **Handled:** the pipeline does the right thing.
- ⚠️ **Gap:** the pipeline does something wrong or costly.
- ℹ️ **Limitation:** it's accepted, or the pipeline can't detect it.

**Duplicate Claude cost?** Whether a retry of the task, or a rerun of the week, pays Claude again for an input it already processed. Within a run, a failed task is retried up to 3 times (`retries=3` in the DAG).

## What "fails" means

When a row says a task fails, the program doesn't exit. Airflow is running all the time, and each task attempt runs in its own process. A failure goes like this:

1. **An exception is raised and nothing catches it.** For example, `raise_for_status()` raises `HTTPError`, or `strptime` raises `ValueError`. It travels up out of the task function, so the rest of the function doesn't run.
2. **Airflow catches it, and that attempt ends.** Only the process of that attempt ends. The scheduler and Airflow keep running.
3. **The task is marked `up_for_retry`.** With `retries=3`, Airflow waits (2, 4 and then 8 minutes) and runs the whole function again from the start. Nothing is remembered between attempts, so whatever ran before the exception runs again. That's why `fetch_auctions` makes every BOE call before any Claude call.
4. **If the last attempt also raises, the task is marked `failed`.** Only then does `on_failure_callback` run, which pings `/fail` on healthchecks.io.
5. **The tasks after it are marked `upstream_failed` and don't run.** For example, if `fetch_auctions` fails, `load_auctions`, silver, gold and `ping_success` are all skipped.
6. **The DAG run is marked `failed`.** It isn't repeated on its own: with `catchup=True`, Airflow only creates runs for scheduled times that don't have a run yet. This one has a run, just a failed one. To rerun it, clear it in the UI.

## Bronze

`fetch_auctions` downloads the whole week before `load_auctions` inserts anything, so the week is loaded whole or not at all.

Inside `fetch_auctions`, every BOE call (the 7 summaries, then the announcement of every candidate) comes before any Claude call. So a BOE failure never repeats Claude: Claude is only called again when Claude itself fails.

| Id | Case | What happens | Stored | Duplicate Claude cost? | Status |
|---|---|---|---|---|---|
| B1 | No BOE published that day (404) | The day is skipped | Nothing | No | ✅ |
| B2 | BOE API down or answers with an error | `fetch_auctions` fails, and the whole week is retried | Nothing for the week | No, it fails before Claude is called | ✅ |
| B3 | A title doesn't match `AUCTION_TITLE_RE` | Skipped, with no log | Nothing | No | ℹ️ A real auction with unusual wording is lost without notice |
| B4 | A title matches `NON_AUCTION_TITLE_RE` (correction, suspension...) | Skipped, with no log | Nothing | No | ✅ |
| B5 | An item of the summary has no `url_xml` | Skipped, with no log | Nothing | No | ℹ️ |
| B6 | Claude classifies a title as not an auction | Skipped, with no log | Nothing | Yes, if the week runs again | ℹ️ Cheap call, but nothing records the decision |
| B7 | Claude classifies a correction as an auction by mistake | Loaded as a new auction | Bronze, then silver | No | ℹ️ It can appear as a duplicate auction in the app |
| B8 | Claude refuses or is cut off when classifying a title | `RuntimeError`, `fetch_auctions` fails | Nothing for the week | Yes, on every retry | ⚠️ If it's permanent, the whole week is never loaded |
| B9 | Claude API down | `fetch_auctions` fails, and the week is retried | Nothing for the week | Yes | ✅ |
| B10 | The announcement XML can't be downloaded | `fetch_auctions` fails | Nothing for the week | No, it fails before Claude is called | ✅ |
| B11 | The announcement has no `<texto>` | Stored with an empty text | Bronze | — | ℹ️ Silver then rejects it, probably for having no held date (S5) |
| B12 | The announcement has no `boe_ref` (`metadatos/identificador`) | The insert breaks `NOT NULL`, so `load_auctions` fails | Nothing for the week | No | ⚠️ `errors_handling.md` says `load_auctions` can't fail |
| B13 | The announcement has no publication date | `strptime` fails, so `fetch_auctions` fails | Nothing for the week | No, it fails before Claude is called | ✅ |
| B14 | The announcement is already in bronze (rerun or repeated item) | `ON CONFLICT DO NOTHING` | Nothing new | No | ✅ |
| B15 | A subsequent auction of the same lot (2nd, 3rd...) | New `boe_ref`, loaded as a new announcement | Bronze | — | ✅ By design |
| B16 | A week doesn't run (computer off) | `catchup=True` creates the missed run when Airflow starts | — | — | ✅ |

## Silver

Each announcement has its own transaction: it's stored whole or not at all. Announcements are processed oldest first.

### Announcement

| Id | Case | What happens | Stored | Duplicate Claude cost? | Status |
|---|---|---|---|---|---|
| S1 | Already in `silver.auctions` or `silver.rejected_announcements` | Not pending | — | No | ✅ |
| S2 | Claude API down, rate limited or timing out | Rollback, the run stops, and Airflow retries it | Earlier announcements stay committed | Yes | ✅ |
| S3 | Claude answers with a permanent error (`BadRequestError`, for example a text that's too long) | Same as S2, because `anthropic.APIError` includes permanent errors | Nothing for it or for anything newer | Yes, on every retry and every run | ⚠️ It's processed first on every run, so the pipeline gets stuck on it |
| S4 | Claude refuses, even after the fallback | `RuntimeError` → FAILED, nothing recorded | Nothing | Yes, on every retry and every run | ⚠️ Paid every week, forever |
| S5 | Claude's answer is cut off by `max_tokens` | `RuntimeError` → FAILED, nothing recorded | Nothing | Yes, on every retry and every run | ⚠️ Same as S4 |
| S6 | No held date | Rejected: "No held date" | `rejected_announcements` | No | ✅ |
| S7 | Claude finds no lots | Rejected: "No valid lots" | `rejected_announcements` | No | ✅ |
| S8 | Lots found, but none of them valid | Rejected: "No valid lots" | `rejected_announcements` | No | ✅ |
| S9 | The held date is before the publication date, or otherwise implausible | Stored as it is, because it isn't validated | Silver | No | ℹ️ |
| S10 | Claude extracts a wrong but valid value (a wrong price, for example) | Stored | Silver | No | ℹ️ Can't be detected |
| S11 | The prompt or the model changes | Old rows keep their extraction, and `extraction_prompt_hash` tells them apart | — | No | ✅ By design |
| S12 | Any announcement is FAILED | The silver task fails, so gold and the success ping don't run | — | — | ⚠️ One FAILED announcement stops gold from refreshing that week |
| S13 | The run stops midway (container restart) | The open transaction is rolled back, and the rerun continues | Earlier announcements stay committed | Only for the one interrupted | ✅ |
| S14 | Two runs process silver at the same time (several catchup runs) | Both select the same pending announcements. The second insert breaks `UNIQUE (boe_ref)` → FAILED in that run | One copy | Yes, both runs pay for it | ⚠️ No `max_active_runs` is set, so Airflow allows several runs at once |

### Lot

| Id | Case | What happens | Stored | Duplicate Claude cost? | Status |
|---|---|---|---|---|---|
| S15 | A lot has no starting price | The lot is skipped and logged as REJECTED | The rest of the announcement | No | ℹ️ The lot is only in the log, not in the database |
| S16 | A lot has no catastral references | Skipped: no valid reference | The rest of the announcement | No | ℹ️ Same as S15 |
| S17 | A lot has some invalid references | Stored with only the valid ones | Silver | No | ⚠️ Its surface is too small, so its price per m² is wrong, and nothing marks it |
| S18 | Two lots with the same `lot_number` | The insert breaks `UNIQUE (auction_id, lot_number)` → FAILED | Nothing | Yes, every run | ⚠️ Same loop as S4 |
| S19 | A negative starting price | The insert breaks `CHECK (starting_price >= 0)` → FAILED | Nothing | Yes, every run | ⚠️ Same loop as S4 |
| S20 | A price too big for `NUMERIC(14, 2)` | Numeric overflow → FAILED | Nothing | Yes, every run | ⚠️ Unlikely |

### Catastral reference

| Id | Case | What happens | Stored | Duplicate Claude cost? | Status |
|---|---|---|---|---|---|
| S21 | Not 20 characters after normalising | Skipped and logged | Nothing | No | ✅ |
| S22 | Doesn't exist in Catastro (404, or 502 while the test reference works) | Skipped and logged | Nothing | No | ✅ |
| S23 | Exists, but a required field is empty | Skipped and logged | Nothing | No | ✅ |
| S24 | Has no crops (an apartment, for example) | Stored with `qualification` NULL | Silver | No | ✅ |
| S25 | Goolzoom down (502 for the test reference too) | The run stops, and Airflow retries it | Earlier announcements stay committed | Yes, for the current one | ✅ |
| S26 | Goolzoom answers with another error (401 bad key, 429 quota, 500) | The run stops, like S25 | Same as S25 | Yes | ℹ️ Right for a bad key or quota. A 500 for only one reference would make the pipeline stuck, like S3 |
| S27 | Goolzoom answers with an unexpected structure (a missing key, an empty `properties` list) | `KeyError` / `IndexError` → FAILED | Nothing | Yes, every run | ⚠️ Same loop as S4 |
| S28 | Already stored, from an earlier auction or lot | Its id is reused, with no Goolzoom call | — | No | ✅ This is how re-auctions are linked |
| S29 | Repeated in the same lot (written with and without spaces) | `ON CONFLICT DO NOTHING` in the junction table | One link | No | ✅ |
| S30 | Invalid, and appears again later | Goolzoom is called again every time, because invalid references aren't recorded | Nothing | No | ℹ️ Costs Goolzoom calls, not Claude |
| S31 | A value longer than its column (`VARCHAR(100)`) | The insert fails → FAILED | Nothing | Yes, every run | ⚠️ Unlikely |

## Gold

| Id | Case | What happens | Status |
|---|---|---|---|
| G1 | The load fails midway | One transaction, so the previous gold stays | ✅ |
| G2 | The references of a lot have different values (province, use, qualification...) | `gold.app_lots` shows the most common one, or the first alphabetically if there is a tie | ℹ️ By design |
| G3 | None of the references of a lot has a qualification | `qualification` is NULL | ✅ |
| G4 | `source_url` doesn't contain `/xml.php` | `announcement_url` stays as the XML link | ℹ️ |
