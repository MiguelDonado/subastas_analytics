# Failure modes

Every decision point in the pipeline, one row each, so it's possible to check that every case is covered. Each row has an id (`B1`, `S1`, `G1`...) so a test can point to the row it proves.

This table was built by reading the code, not by running it. No row has a test yet.

**Status:**
- ✅ **Handled:** the pipeline does the right thing.
- ⚠️ **Gap:** the pipeline does something wrong or costly.
- ℹ️ **Limitation:** it's accepted, or the pipeline can't detect it.

**Duplicate Claude cost?** Whether a retry of the task, or a rerun of the week, pays Claude again for an input it already processed. Within a run, a failed task is retried up to 3 times (`retries=3` in the DAG).

**Rule for cases that have never happened:** prefer the simplest behaviour that alerts over clever recovery. Recovery code for something that has never happened is never tested by real data: the first time it runs is exactly when the format has changed, so it's when it's least trustworthy, and it can hide the change. When it does happen, you'll see the real new format and can write the right fix instead of guessing it now. For example, B5 skips and logs a candidate with no `url_xml` instead of building the URL, and B17 alerts if it happens to every item.

## What "fails" means

When a row says a task fails, the program doesn't exit. Airflow is running all the time, and each task attempt runs in its own process. A failure goes like this:

1. **An exception is raised and nothing catches it.** For example, `raise_for_status()` raises `HTTPError`, or `strptime` raises `ValueError`. It travels up out of the task function, so the rest of the function doesn't run.
2. **Airflow catches it, and that attempt ends.** Only the process of that attempt ends. The scheduler and Airflow keep running.
3. **The task is marked `up_for_retry`.** With `retries=3`, Airflow waits (2, 4 and then 8 minutes) and runs the whole function again from the start. Nothing is remembered between attempts, so whatever ran before the exception runs again. That's why `fetch_auctions` makes every BOE call before any Claude call.

   A retry only repeats the failed task, not the DAG run from the beginning. For example, if `transform_auctions` fails, bronze isn't run again. This works because the return value of a task that succeeded (its XCom) is stored in Airflow's metadata database, so the next task reads it from there, even in a different process. Silver reads the same output of `fetch_auctions` on every attempt.

   Airflow keeps XComs "forever": it never deletes them on its own. An XCom is only deleted when its own task runs again, when `airflow db clean` is run by hand, or when the metadata database is wiped (`astro dev kill`, or deleting its volume).
4. **If the last attempt also raises, the task is marked `failed`.** Only then does `on_failure_callback` run, which pings `/fail` on healthchecks.io.
5. **The tasks after it are marked `upstream_failed` and don't run.** For example, if `fetch_auctions` fails, `parse_auctions`, `load_auctions`, silver, gold and `ping_success` are all skipped.
6. **The DAG run is marked `failed`.** It isn't repeated on its own: with `catchup=True`, Airflow only creates runs for scheduled times that don't have a run yet. This one has a run, just a failed one. To rerun it, clear it in the UI with **"Only failed"**. That reruns the failed task and the ones after it (`upstream_failed`), while the tasks that succeeded keep their state and their XCom, so their Claude calls aren't repeated. Clearing the whole run instead starts again from `fetch_auctions`, and Claude classifies the titles again.

## Bronze

Bronze has three tasks, and the whole week goes through each one before the next starts, so the week is loaded whole or not at all:

1. **`fetch_auctions`:** downloads the 7 summaries, skips the candidates whose `boe_ref` is already in `bronze.auctions` (B14), downloads the raw XML of the rest, then asks Claude about each title. Every BOE call comes before any Claude call, so a BOE failure never repeats Claude. It returns the XML of the titles Claude confirmed as auctions.
2. **`parse_auctions`:** parses that XML into the rows of `bronze.auctions`. It's its own task so that a parse error (B11, B12, B13) never calls Claude again: `fetch_auctions` already succeeded and its XCom is stored, both for a retry and when the run is cleared with "Only failed". It has `retries=0`, because a parse error gives the same result on every attempt, so it alerts right away.
3. **`load_auctions`:** inserts the rows.

### Why B17 alerts after 2 weeks

B17 alerts after **2 weeks** in a row with no candidates. That's a deliberate choice: a false alarm once or twice a year is better than missing auctions.

**The data** (weekly candidates in BOE summaries from 2025 and 2026):
- A week with 0 candidates is common: about 1 in 7 weeks.
- The longest run of 0 weeks found was 2, in August 2025 (the runs of 4 and 11 August). August 2026 never had 2 in a row. Easter and Christmas 2025 never had more than 1.
- So a 2-week threshold gives about 1 or 2 false alarms a year, most likely in August.

**Why not a higher threshold (4 or 5 weeks) to avoid them:** the time between an announcement being published and the deadline for presenting offers can be short. For example, about 3 weeks for an auction in Soria. With a 5-week threshold, a broken regex would only alert after that deadline had passed, so the auction would be missed. The BOE keeps every summary, so the data could still be loaded later, but the chance to take part in the auction would be gone.

**What to do with a false alarm:** check the `NEAR MISS` lines in the log and search the BOE. If there really were no auctions, the failed run had nothing to load: leave it failed or mark it as success in the UI.

## Silver

Each announcement has its own transaction: it's stored whole or not at all. Announcements are processed oldest first.
