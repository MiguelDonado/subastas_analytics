# CI/CD

## The tests workflow

`.github/workflows/tests.yml` runs the tests on GitHub on every pull request to `main`, and again on every push to `main` (after a merge).

It has two jobs. Each one runs on its own fresh Ubuntu machine, both at the same time, and each shows up as its own check on the pull request:

| Job | Runs | Takes |
|---|---|---|
| `unit-and-integration` | `uv sync`, then `uv run pytest` | About a minute. GitHub's Ubuntu machines come with Docker, so testcontainers can start Postgres there |
| `dags` | Installs the Astro CLI, then `astro dev pytest tests/dags` | A few minutes, because it builds the Airflow image |

- **No secrets needed.** The tests never call a real API (see the safety net in `docs/7.testing.md`), so the workflow needs no API keys. `.env` isn't in git, so the `dags` job creates an empty one, because `astro dev pytest` looks for it.
- **A check fails:** open the **Checks** tab of the pull request to see the log. Fix it and push to the same branch: the checks run again on their own.

## Protecting the main branch

A GitHub ruleset stops direct pushes to `main`, and stops a pull request from merging until both checks pass. Strictly speaking it's a repo setting rather than CI, but it's what makes CI useful: without it, a red check is only a warning.

### Set up the ruleset

On the repo's GitHub page:

1. Go to **Settings → Rules → Rulesets → New ruleset → New branch ruleset**.
2. Give it a name, like `protect-main`, and set **Enforcement status** to **Active**.
3. Leave **Bypass list** empty, so the rules also apply to me.
4. Under **Target branches**, choose **Add target → Include default branch**.
5. Under **Rules**, enable these:
   - **Require a pull request before merging**, with **Required approvals** set to 0
   - **Require status checks to pass**: click **Add checks** and select `unit-and-integration` and `dags`
   - **Block force pushes**
   - **Restrict deletions**
6. Click **Create**.

### Things to watch for

- **Working alone:** **Required approvals** has to be 0. GitHub doesn't let me approve my own pull request, so requiring 1 would block me from merging.
- **A check can only be selected after it has run once.** GitHub only offers the checks it has already seen. Until then, the ruleset has no checks to wait for, so pull requests merge without them.
- **An invalid workflow file runs nothing.** If `tests.yml` isn't valid YAML (for example, a line indented too far), GitHub can't read it, so no job starts, not even the valid one, and it sends an email saying no jobs were run. With no checks required yet, the pull request still merges. That's what happened when the workflow was first added: `run:` was indented further than `name:` in the same step.
