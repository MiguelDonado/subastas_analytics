# Performance

The app is used by 1 to 3 people, but it should still feel fast. It was fast when the database was local, and became slower after moving the database to Neon and the app to Posit Connect Cloud. Running the app locally with only the database on Neon was still slow, so the time goes in talking to the database.

**In short: the biggest benefit came from moving the database next to the app.** With Neon in Frankfurt and Posit in Ohio, every round trip between the app and the database cost ~100 ms: each query paid one, and each new connection about four. With both in Ohio, a round trip costs ~1–2 ms, so queries and connections became cheap at the same time. The pool and fewer queries only shorten the trips; the move made them almost free.

## What a round trip is

A round trip is one message going from the app to the database, plus the answer coming back. It's the travel time over the network, whatever the message is.

`SELECT 1` is how it's measured: the database does almost no work for it and the answer is tiny, so its time is almost only the travel. Comparing it with a real query shows how much of that query is network and how much is the database's work.

From the laptop to Neon in Frankfurt, where it was until it moved to Ohio, a round trip took about **85 ms**. Every query costs at least that.

## Where the time went

Before the changes, every database access opened a new connection, ran its queries and closed it:

| Action | Connections opened | Queries |
|---|---|---|
| Login | 1 | 1 |
| Start of the app (`read_app_data`) | 1 | 2 (lots, references) |
| Each **Buscar** | 1 | 1 (all the user's reviews) |
| Each **row click** | 1 | 1 (all the user's reviews, then filtered to one lot in R) |
| Each **Guardar** | 1 | 2 (save, then all the user's reviews again to refresh the table) |

Opening a connection isn't one round trip but about four: open the network connection, agree on the encryption (TLS), and check the password. So every click paid for a whole new connection before running its query.

Two more delays don't depend on the app's code:

- **Neon goes to sleep** after a few minutes without connections (free plan). The first query after that waits for it to wake up.
- **Posit stops the app** when nobody uses it. The first visitor wakes it up: Posit starts a new R process, which runs `app.R` from the top before the visitor's session starts.

## Measures, in order

1. **Measure first.** Time each step separately, to find where the time really goes before changing anything.
2. **Fewer connections, with a pool.** Keep a connection open and reuse it for every query. Done, see below.
3. **Fewer queries.** Not done, on purpose. A row click could reuse the reviews already read instead of reading them again, and Guardar could update the changed row in R instead of reading every review after saving. But:
   - **Since the move to Ohio, a query costs ~1–2 ms**, against ~100 ms before. Removing one would save time nobody notices, next to the ~100 ms between the browser and the app, which no change to the queries can touch.
   - **The database stays the single source of truth.** Fewer queries would mean keeping a copy of the notes in R and trusting it, and that copy could get out of date, for example when two people use the same user. See "The database is the only source of the notes" in `11.reviews.md`.
4. **The database closer to the app.** Done: Neon moved to Ohio, the region where Posit runs the app. See "Where the database should be".

## How it's measured

`scripts/try_db_times.R` times the app's queries against the database in `dashboard/.Renviron` (Neon). It's read-only. Run it from `dashboard/`, so renv is active and R reads `.Renviron`:

```bash
cd dashboard
Rscript ../scripts/try_db_times.R
```

It measures, in milliseconds:

- **The first connection**, which includes Neon waking up if it was asleep. Run the script after Neon has been idle for more than about 5 minutes to see it.
- **A row click and the start of the app, before the pool:** a new connection every time, as the app did.
- **Creating the pool**, and **the same two actions with the pool.**
- **A row click after 65 s without queries**, to see the pool's check (see "The 60-second check").

Each action runs 5 times, and the script prints the first time, the median and the fastest.

## Results

Measured from the laptop against Neon in Frankfurt, before it moved to Ohio:

| Action | Before (new connection) | With the pool |
|---|---|---|
| Row click or Buscar | ~420 ms | **~88 ms** |
| Start of the app | ~570 ms | **~187 ms** |
| Opening a connection | ~330 ms on every action | ~540 ms to create the pool, once per R process |
| First click after 65 s idle | | ~350 ms |
| First connection after Neon slept | 1.5–2.3 s | the same |

- **Opening the connection was about 80% of each click.** A row click was ~330 ms connecting and ~90 ms running the query.
- **The amount of data doesn't matter.** Each query costs ~90–130 ms, almost the same as `SELECT 1` (~85 ms). Reading 210 lots or 336 references is almost free: what costs is the distance, once per query. Making the queries themselves faster (indexes, fewer columns) would only save the small rest.
- **With the pool, a click is one round trip (~88 ms)**, the minimum for any query from the laptop to Frankfurt. From here, only fewer queries can make it faster.
- **The first click after 65 s idle cost ~350 ms**, more than the check plus the query (~175 ms). It's closer to what opening a new connection costs, so the connection was probably closed during the pause, perhaps by Neon's pooler (the host ends in `-pooler`). Still faster than every click before.
- **Neon's wake-up isn't affected by the pool.** The free plan doesn't allow turning the sleeping off.

## How the pool works

`create_db_pool()` in `R/db.R` creates it with the `pool` package. The query functions receive it as `con`, and DBI functions work the same with a pool as with a connection.

**After the move to Ohio, its gain on Posit is small.** Opening a connection from Posit to Neon is now about 4 round trips of ~1–2 ms, plus a few milliseconds of computing for the encryption and the password check: ~10–20 ms, instead of ~330 ms. Most of what the pool saved before, the move saves now. It stays because:

- **From the laptop it still matters.** Running the app locally against Neon, every new connection crosses the Atlantic: about 4 × ~110 ms per action without the pool.
- **It's built and costs nothing.** Removing it would mean changing code that works and that the e2e tests cover, for no gain.
- **It doesn't depend on where things run.** If the app and the database ever end up in different regions again, it already protects every action.

- **One connection, reused.** The pool opens one connection when it's created, and only opens another if a query needs one while every open one is lent out. R does one thing at a time, so in this app the pool never needs a second one.
- **Created once per R process, shared by every session.** It's created at the top level of `app.R`, which runs once when the R process starts, not once per session. On Posit, the first visitor wakes the app, Posit starts the R process, and the pool is created. The next visitors or tabs share it. When nobody uses the app, Posit stops the process and `onStop()` closes the pool.
- **After reading `tests/e2e.Renviron`.** If it were created before, in the e2e tests it would read the Neon values of `.Renviron`, and the tests' safety check (`db_host` must be `localhost`) would fail.
- **Sharing it between users is safe.** Each query borrows the connection and returns it straight away. What keeps each user's notes apart is the `WHERE user_id = $1` of the queries, not the connection: every user already connected as the same database user, `subastas_app`. Sharing would only be a problem with several queries that must run on the same connection, like a transaction (`BEGIN` ... `COMMIT`). The app has none. If one is ever added, it needs `pool::poolWithTransaction()`.

### The 60-second check

An open connection can die without the app knowing: Neon going to sleep closes it, and so can a network glitch. A query on a dead connection doesn't fail silently, it fails with an error. In the app, that ends the session (the "Se ha perdido la conexión con el servidor" screen), or breaks the table and the map, or fails the login.

So, if a connection hasn't been used for more than 60 seconds, the pool checks it with a trivial query before lending it. Nothing in `R/db.R` sets this: it's a default of `pool` (`validationInterval` in `dbPool()`). If the check fails, the pool throws that connection away and opens a new one, and the real query never sees the dead connection.

| Situation | Extra cost of that first click |
|---|---|
| Last query less than 60 s ago | None |
| More than 60 s idle, connection alive | ~85 ms, the check |
| More than 60 s idle, connection dead | ~85 ms + ~330 ms for a new connection (+ Neon's wake-up if it was asleep) |

The pool doesn't use the connection directly and retry only if the query fails. It doesn't know what the query does, so it can't know if repeating it is safe: a write could end up applied twice. And a failed query would need handling in every place that queries.

The trade-off: **~85 ms on the first click after a pause, in exchange for never seeing an error caused by a dead connection, with no extra code.** With 1–3 users it's clearly worth it.

### The login receives the pool

`check_user` couldn't read `db_pool` as a global variable. Shiny loads the files in `R/` into a different environment than `app.R`, and a function only looks for missing variables in the environment where it was defined and its parents, never in `app.R`'s.

So `make_check_user(pool)` in `R/auth.R` returns the login function with the pool inside it (a closure), and `app.R` passes it to shinymanager: `secure_server(check_credentials = make_check_user(db_pool))`. shinymanager still calls it with only `(user, password)`.

## Where the database should be

The browser never talks to the database, only the app does:

```
Browser (Spain)  ──1 round trip──▶  App (Posit)  ──1 round trip per query──▶  Neon
```

A click is one round trip between the browser and the app, but one round trip per query between the app and the database. So the distance between the app and the database gets multiplied, and the one between the browser and the app doesn't. With rough numbers (Spain to the US ~100 ms, within the same region ~1–5 ms):

| Layout | Row click (1 query) | Guardar (2 queries) |
|---|---|---|
| App in the US, Neon in Frankfurt | ~200 ms | ~300 ms |
| App in the US, Neon in the US | ~105 ms | ~110 ms |
| App and Neon both in Europe | ~45 ms | ~50 ms |

For this project, **the database close to the app matters more than the app close to the browser**. Best of all is both together and both close to the users. The pipeline also writes to Neon from the laptop in Spain, but once a week and unattended, so its distance doesn't matter.

Posit's support confirmed that Posit Connect Cloud runs the apps in AWS `us-east-2` (Ohio), and Neon was in Frankfurt, so every query of the app crossed the Atlantic. Posit can't choose its region, but Neon can, so the database moved to **AWS US East 2 (Ohio)**. How: "Moving Neon to Posit's region" in `4.deployment.md`.

One round trip on each side of the app:

| | Browser (Spain) ↔ app (Ohio) | App (Ohio) ↔ database |
|---|---|---|
| Before the move (Neon in Frankfurt) | ~100 ms | ~100 ms per query |
| After the move (Neon in Ohio) | ~100 ms | almost 0 ms per query (~1–2 ms) |

The browser–app part doesn't change, because Posit stays where it is. What the move removes is the ~100 ms that every query paid. A click with one query goes from ~200 ms to ~100 ms, and the more queries an action makes, the more it saves. These are typical latencies between those regions, not measured from Posit.

What gets slower is everything that talks to Neon from the laptop in Spain: the weekly pipeline, running the app locally against Neon, and DBeaver. The e2e tests and CI aren't affected, because they use their own Postgres. The fewer queries per click, the less the location matters.

## Slow `astro dev start`

`astro dev start` took very long because the Airflow image copied files it doesn't need. The Astro base image copies the whole project into the image (`COPY . .`), except what `.dockerignore` lists, and it didn't list these folders:

| Folder | Size |
|---|---|
| `assets/videos` | 4.6 GB |
| `dashboard/renv` | 422 MB |
| `docs/miscellaneous` | 114 MB |

So every build sent ~5 GB to Docker and wrote it into the image. Also, changing any of those files, like a video or a doc, broke Docker's cache, and the `pip install` in the `Dockerfile` ran again.

Now `.dockerignore` lists `assets`, `dashboard`, `docs`, `data_modeling`, `tests` and `.pytest_cache`. Airflow only needs `dags/`, `include/`, `plugins/`, `src/`, `pyproject.toml`, `requirements.txt` and `packages.txt`.
