# Testing

## Where the tests run

The tests are split in two, and each part runs in a different place:

| Tests | Folder | Command | Runs |
|---|---|---|---|
| Unit and integration | `tests/unit`, `tests/integration` | `uv run pytest` | On the computer, with the project's `.venv` |
| DAG | `tests/dags` | `astro dev pytest tests/dags` | Inside the Astro container |

- **The DAG tests run in the container** because they need Airflow, which is only installed in the Astro image, not in the `.venv`.
- **The rest run on the computer.** See `testpaths` below.
- **Only the fast ones:** `uv run pytest -m "not integration"` skips the integration tests, so it needs no Docker and takes under a second.

## pytest settings

`pyproject.toml` has a `[tool.pytest.ini_options]` section, which changes how pytest behaves. pytest reads it on its own every time it runs:

```toml
[tool.pytest.ini_options]
testpaths = ["tests/unit", "tests/integration"]
addopts = ["--strict-markers"]
markers = [
    "integration: needs Docker, it starts a Postgres container. Skip them with -m 'not integration'",
]
```

| Setting | What it does |
|---|---|
| `testpaths` | The folders pytest searches when no path is given. It leaves `tests/dags` out, so a plain `uv run pytest` doesn't fail trying to import Airflow. Giving a path yourself (`uv run pytest tests/dags`) ignores it |
| `addopts` | Options added to every `pytest` command, as if they were typed. `--strict-markers` turns a marker that isn't declared (a typo like `@pytest.mark.integraton`) into an error. Without it, the typo would only be a warning, and the mark would quietly do nothing |
| `markers` | The markers the tests can use, with a description. Because of `--strict-markers`, a marker has to be listed here before a test can use it. Each integration test file marks all its tests at once with `pytestmark = pytest.mark.integration` |

## Integration tests

They run `load_silver` against a real Postgres, with only the APIs faked:

| Real | Faked (in `tests/integration/conftest.py`) |
|---|---|
| Postgres 17, the `.sql` files in `include/sql`, and `load_silver` with its commits, rollbacks and savepoints | Claude (`claude`), Goolzoom (`goolzoom`) and the failure alert (`ping`) |

- **One Postgres for the whole run.** It starts once, the tables are created once from `create_bronze_auctions.sql` and `create_silver.sql`, and the container is deleted at the end.
- **Empty tables for every test.** `load_silver` commits, so a rollback can't undo what a test did. Every table is emptied with `TRUNCATE` before each test instead.
- **The fakes are always on.** `load_silver` calls all three, so a test that forgot one would reach the real function. A test asks for a fake by name only to change its answer (`claude.answers["BOE-B-2"] = ...`) or to count its calls.
- **Each call to the fake Claude is a call that would be paid.** That's how `test_silver_costs.py` checks that nothing is paid twice.

## Why not run every test in the Astro container

The integration tests can't run there.

Each integration test run starts its own Postgres container with testcontainers, and deletes it at the end. testcontainers doesn't start the container itself: it asks Docker to do it, through the file `/var/run/docker.sock`.

- **On the computer**, that file exists, so it works. It's the same way `astro dev start` starts the Airflow containers.
- **Inside the Astro container**, that file doesn't exist, so there's no Docker to ask, and the tests fail before they start.

Giving the Astro container access to Docker would fix it, but `astro dev pytest` has no option for that.

In CI, they'll be two steps of the same workflow, and a pull request merges only if both pass.

## Fixture or plain function

A helper is a fixture only when it needs something that only pytest can give it. Otherwise it's a plain function, which is simpler.

| Use | When | Examples |
|---|---|---|
| Fixture | It needs `monkeypatch` or another fixture, or something has to be undone after the test | `block_real_apis`, `claude`, `add_bronze` |
| Plain function, in the test file | It only builds data from its arguments, and it's used in one file | `fake_response`, `summary_item`, `announcement_xml` |
| Plain function, in `helpers.py` | The same, but used in several files | `announcement`, `lot`, `claude_error`, `rows` in `tests/integration/helpers.py` |

- **`helpers.py` can be imported** (`from helpers import lot`) because pytest adds the folder of each test file to the places Python imports from.
- **`make_response` is an exception:** it only builds data, but it's a fixture in `tests/conftest.py`. A fixture in a `conftest.py` reaches every test below it without an import. When it was written, there was no helpers module to put it in.
