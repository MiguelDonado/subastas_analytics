# Testing

## Where the tests run

The tests are split in two, and each part runs in a different place:

| Tests | Folder | Command | Runs |
|---|---|---|---|
| Unit and integration | `tests/unit`, `tests/integration` | `uv run pytest` | On the computer, with the project's `.venv` |
| DAG | `tests/dags` | `astro dev pytest tests/dags` | Inside the Astro container |
| App end-to-end (e2e) | `dashboard/tests/testthat` | `shinytest2::test_app()` in R, from `dashboard/` | On the computer, with the app's renv, a local Postgres and Google Chrome |

- **The DAG tests run in the container** because they need Airflow, which is only installed in the Astro image, not in the `.venv`.
- **The rest run on the computer.** See `testpaths` below.
- **Only the fast ones:** `uv run pytest -m "not integration"` skips the integration tests, so it needs no Docker and takes under a second.

## pytest settings

`pyproject.toml` has a `[tool.pytest.ini_options]` section, which changes how pytest behaves. pytest reads it on its own every time it runs:

```toml
[tool.pytest.ini_options]
testpaths = ["tests/unit", "tests/integration"]
addopts = ["--strict-markers"]
pythonpath = ["dags"]
markers = [
    "integration: needs Docker, it starts a Postgres container. Skip them with -m 'not integration'",
]
```

| Setting | What it does |
|---|---|
| `testpaths` | The folders pytest searches when no path is given. It leaves `tests/dags` out, so a plain `uv run pytest` doesn't fail trying to import Airflow. Giving a path yourself (`uv run pytest tests/dags`) ignores it |
| `addopts` | Options added to every `pytest` command, as if they were typed. `--strict-markers` turns a marker that isn't declared (a typo like `@pytest.mark.integraton`) into an error. Without it, the typo would only be a warning, and the mark would quietly do nothing |
| `pythonpath` | Folders added to the places Python imports from. `dags` lets the DAG tests `import subastas_pipeline`: Airflow finds the DAG file with its own loader, so the folder isn't importable otherwise |
| `markers` | The markers the tests can use, with a description. Because of `--strict-markers`, a marker has to be listed here before a test can use it. Each integration test file marks all its tests at once with `pytestmark = pytest.mark.integration` |

## Integration tests

They run the loaders and the SQL against a real Postgres, with only the APIs faked:

| Real | Faked (in `tests/integration/conftest.py`) |
|---|---|
| Postgres 17, the `.sql` files in `include/sql`, `insert_auctions`, and `load_silver` with its commits, rollbacks and savepoints | Claude (`claude`), Goolzoom (`goolzoom`) and the failure alert (`ping`) |

- **One Postgres for the whole run.** It starts once, the bronze, silver and gold tables are created once from their `create_*.sql` files, and the container is deleted at the end.
- **Gold is loaded as Airflow does it.** `test_gold.py` runs the whole `load_gold.sql` in one execute and then commits, the same as `SQLExecuteQueryOperator` by default.
- **Empty tables for every test.** `load_silver` commits, so a rollback can't undo what a test did. Every table is emptied with `TRUNCATE` before each test instead.
- **The fakes are always on.** `load_silver` calls all three, so a test that forgot one would reach the real function. A test asks for a fake by name only to change its answer (`claude.answers["BOE-B-2"] = ...`) or to count its calls.
- **Each call to the fake Claude is a call that would be paid.** That's how `test_silver_costs.py` checks that nothing is paid twice.

## DAG tests

`tests/dags/test_subastas_pipeline.py` checks the DAG itself: that it imports, its settings (schedule, `catchup`, `max_active_runs`, retries), the task order, and what its own tasks do.

- **A task is tested as a plain function.** `dag.get_task("bronze.fetch_auctions").python_callable` is the function behind the task, and the test calls it directly. Airflow isn't running.
- **Everything the tasks call is faked in the DAG module** (`subastas_pipeline`): the BOE, Claude, `PostgresHook` and the loaders. The loaders themselves are already covered by the unit and integration tests.
- **The safety net applies here too.** `tests/conftest.py` is above `tests/dags`, so no DAG test can call a real API either.
- **`astro dev pytest` rebuilds the image first**, so it picks up the current tests and code. The first run after a change takes a few minutes.

## App end-to-end (e2e) tests

They start the real Shiny app, open it in a Chrome without a window, and use it like a person would: they click, type and check what changed. They're written with shinytest2.

| Test | File | What it checks |
|---|---|---|
| Search and select | `test-search-select.R` | Turning off "Solo subastas activas" and clicking Buscar shows more lots and moves the map. Clicking the first row selects it and zooms the map in to its parcels |
| Note and status | `test-note-status.R` | After saving a status and a note, the selected row shows them. Deselecting the row empties the card and disables Guardar. Selecting it again brings back the saved values and enables Guardar |
| Marker | `test-marker.R` | Clicking the only marker in Valladolid selects its lot's row, moving the table to its page, zooms the map in to it, and opens its popup with its catastral reference |

### How to run them

1. Google Chrome installed in `/usr/bin/google-chrome`.
2. The container `subastas-db-e2e` stopped, because `setup.R` starts its own.
3. In R, from `dashboard/`: `shinytest2::test_app()`. From a terminal: `NOT_CRAN=true Rscript -e 'shinytest2::test_app(".")'`. Without `NOT_CRAN=true`, shinytest2 skips the tests.

### The database

They use the local Postgres from before the move to Neon. Its data is still in the Docker volume `subastas-analytics_42239a_subastas_db_data`, and nothing writes to it any more, so the lots are always the same.

- **`setup.R` starts it and stops it.** testthat runs it once before the tests. It starts Postgres 17 on that volume on `localhost:5435`, waits until it accepts connections, and stops it when the tests end, even if one fails.
- **The app connects with `tests/e2e.Renviron`**, as `subastas_app`, the same user as on Neon, so it has the same permissions. In test mode, `app.R` reads that file itself. Setting the variables in `setup.R` doesn't work: the app runs in its own R process, which reads `dashboard/.Renviron` when it starts, and its Neon values win.
- **Each test first checks that the app isn't on Neon.** The app exports its database host with `exportTestValues(db_host = ...)`, and the test checks it's `localhost` before doing anything else.
- **The user `test` (password `test`)** exists only in the local database, for these tests.
- **Test 2 deletes the notes of `test`**, at the start and at the end (`delete_test_reviews()` in `helper-db.R`). It deletes them straight from the database, not through the app, so it works even if a check fails while no row is selected.

### What changes in test mode

shinytest2 starts the app with `shiny.testmode` turned on, and `is_testmode()` in `app.R` checks it. On Posit Connect Cloud it's off, so none of this happens there.

| What | Why |
|---|---|
| No login screen. The app starts as the user `test` | After a correct login, shinymanager reloads the page, and shinytest2 can't follow a reload |
| "Today" is always 2026-11-18 | "Solo subastas activas" compares the deadlines with today. With a fixed date, the active lots are the same on every run |
| The app reads `tests/e2e.Renviron` | So it connects to the local database, not Neon |

The login itself isn't covered by these tests.

### Clicking a row or a marker

shinytest2's `app$click()` only sends a `click` event, but DT selects a row on `mousedown`, so the click did nothing. `click_row()` in `helper-click.R` sends the three events a real mouse sends, in order: `mousedown`, `mouseup` and `click`. Buttons like Guardar are clicked with `app$click()`, because Shiny buttons react to `click`.

`click_marker()` in `helper-click.R` clicks a marker with a real mouse click instead:

1. It asks Leaflet where the marker of a catastral reference is on the page, in pixels. In `app.R` each marker's id is its catastral reference.
2. It tells Chrome to press and release the left mouse button at that position. To the page it's the same as a person clicking, so there's no need to know which events Leaflet listens to. If the marker were hidden or covered, the click would land on something else and the test would fail.

### Waiting instead of reading right away

Every action goes from Chrome to the app and back, so the tests wait before checking:

- **`app$wait_for_value()`** waits until a value is there, or until it's different from an old one with `ignore`. "The map moved" is checked by waiting until `map_bounds` (which Leaflet sends to Shiny every time the map moves) differs from before. If it never changes, the wait times out and the test fails.
- **`app$wait_for_idle()`** waits until the app has finished everything an action started. For example, after Buscar the table is also redrawn, and a click before that lands on the old table.

## Why not run every test in the Astro container

The integration tests can't run there.

Each integration test run starts its own Postgres container with testcontainers, and deletes it at the end. testcontainers doesn't start the container itself: it asks Docker to do it, through the file `/var/run/docker.sock`.

- **On the computer**, that file exists, so it works. It's the same way `astro dev start` starts the Airflow containers.
- **Inside the Astro container**, that file doesn't exist, so there's no Docker to ask, and the tests fail before they start.

Giving the Astro container access to Docker would fix it, but `astro dev pytest` has no option for that.

In CI, they'll be two steps of the same workflow, and a pull request merges only if both pass.

## Fixture or plain function

A helper is a fixture only when it needs something that only pytest can give it. Otherwise it's a plain function, which is simpler.

| Use | When | Examples |
|---|---|---|
| Fixture | It needs `monkeypatch` or another fixture, or something has to be undone after the test | `block_real_apis`, `claude`, `add_bronze` |
| Plain function, in the test file | It only builds data from its arguments, and it's used in one file | `fake_response`, `summary_item`, `announcement_xml` |
| Plain function, in `helpers.py` | The same, but used in several files | `announcement`, `lot`, `claude_error`, `rows` in `tests/integration/helpers.py` |

- **`helpers.py` can be imported** (`from helpers import lot`) because pytest adds the folder of each test file to the places Python imports from.
- **`make_response` is an exception:** it only builds data, but it's a fixture in `tests/conftest.py`. A fixture in a `conftest.py` reaches every test below it without an import. When it was written, there was no helpers module to put it in.
