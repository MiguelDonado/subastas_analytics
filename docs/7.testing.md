# Testing

## Where the tests run

The tests are split in two, and each part runs in a different place:

| Tests | Folder | Command | Runs |
|---|---|---|---|
| Unit and integration | `tests/unit`, `tests/integration` | `uv run pytest` | On the computer, with the project's `.venv` |
| DAG | `tests/dags` | `astro dev pytest tests/dags` | Inside the Astro container |

- **The DAG tests run in the container** because they need Airflow, which is only installed in the Astro image, not in the `.venv`.
- **The rest run on the computer.** See `testpaths` below.

## pytest settings

`pyproject.toml` has a `[tool.pytest.ini_options]` section, which changes how pytest behaves. pytest reads it on its own every time it runs:

```toml
[tool.pytest.ini_options]
testpaths = ["tests/unit"]
addopts = ["--strict-markers"]
```

| Setting | What it does |
|---|---|
| `testpaths` | The folders pytest searches when no path is given. It leaves `tests/dags` out, so a plain `uv run pytest` doesn't fail trying to import Airflow. Giving a path yourself (`uv run pytest tests/dags`) ignores it |
| `addopts` | Options added to every `pytest` command, as if they were typed. `--strict-markers` turns a marker that isn't declared (a typo like `@pytest.mark.integraton`) into an error. Without it, the typo would only be a warning, and the mark would quietly do nothing |

## Why not run every test in the Astro container

The integration tests can't run there.

Each integration test run starts its own Postgres container with testcontainers, and deletes it at the end. testcontainers doesn't start the container itself: it asks Docker to do it, through the file `/var/run/docker.sock`.

- **On the computer**, that file exists, so it works. It's the same way `astro dev start` starts the Airflow containers.
- **Inside the Astro container**, that file doesn't exist, so there's no Docker to ask, and the tests fail before they start.

Giving the Astro container access to Docker would fix it, but `astro dev pytest` has no option for that.

In CI, they'll be two steps of the same workflow, and a pull request merges only if both pass.

## Fixture or plain function

A helper is a fixture only when it needs something that only pytest can give it. Otherwise it's a plain function, which is simpler.

| Use | When | Examples |
|---|---|---|
| Fixture | It needs `monkeypatch` or another fixture, something has to be undone after the test, or it's shared from `conftest.py` | `block_real_apis`, `claude`, `make_response` |
| Plain function | It only builds data from its arguments, and it's used in one file | `fake_response`, `summary_item`, `announcement_xml` |

`make_response` is a fixture only to be shared from `conftest.py`. A plain function there can't be imported, because `tests` isn't a package.
