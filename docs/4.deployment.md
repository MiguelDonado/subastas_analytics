# Deployment

Where each part of the project runs, the other setups that were possible, and how Cloudflare Tunnel would have worked in them.

## Final setup

This is the same setup as `cgm-analytics`:

| Part | Where it runs |
|---|---|
| Airflow containers | My laptop |
| Database | Neon, AWS US East 2 (Ohio) |
| Web application | Posit Connect Cloud, AWS us-east-2 (Ohio) |

```
Airflow (laptop) → Neon ← Web application (Posit Connect Cloud) ← Visitors
```

The database and the web application are in the same region, because every query of the app travels between them. See "Moving Neon to Posit's region" below.

**Live app:** https://01a1e61c-7dc8-69e3-b535-b360f28ed430.share.connect.posit.cloud/

The first visit after a while is slow: both Posit Connect Cloud and Neon go to sleep when nobody uses them, and have to wake up.

The Raspberry Pi isn't part of this setup. It also wasn't going to run the Airflow containers in any of the setups below, because they are heavy and the Pi only has 8 GB of RAM.

Neon and Posit Connect Cloud are already reachable from the internet, so nothing has to be configured to accept incoming connections.

Airflow and the web application connect to the database with different users: Airflow with the owner of the database, and the web application with `subastas_app`, which can only read gold and write the notes. See "Database users" in `11.reviews.md`.

## Moving the database to Neon
The commands run inside the local `subastas-db` container, which has `pg_dump` and `psql`. After the move, the container is no longer needed and is commented out in `docker-compose.override.yml`. Its data stays in the Docker volume `subastas_db_data`, as a backup.

### 1. Create a Neon project
`subastas-analytics`, Postgres 17, AWS Frankfurt, database `subastas`. It was later moved to Ohio, see "Moving Neon to Posit's region". Copy the connection string from **Connect** and store it without it showing on screen or in the history:

```bash
read -s NEON_URL
```

Pause the DAG, so nothing is written while copying.

### 2. Copy all the data
`pg_dump` generates the SQL that recreates the local database, and `psql` runs it in Neon:

```bash
docker exec subastas-analytics_42239a-subastas-db-1 \
  pg_dump -U subastas -d subastas --no-owner --no-privileges \
  | docker exec -i subastas-analytics_42239a-subastas-db-1 psql "$NEON_URL"
```

`--no-owner` and `--no-privileges`: the local users don't exist in Neon, so everything is owned by `neondb_owner`, and permissions are given in the next step.

### 3. Create the app's user
`pg_dump` doesn't copy users, so `subastas_app` is created again, as `neondb_owner`:

```bash
docker exec -i subastas-analytics_42239a-subastas-db-1 psql "$NEON_URL" < include/sql/create_app_role.sql
```

Then set its password, as shown in "Setting the password of `subastas_app`" below.

### 4. Check the row counts
Run on both sides and compare:

```bash
COUNT_ROWS="
SELECT table_schema || '.' || table_name AS table_name,
       (xpath('/row/c/text()', query_to_xml(format('SELECT count(*) AS c FROM %I.%I', table_schema, table_name), false, true, '')))[1]::text::int AS row_count
FROM information_schema.tables
WHERE table_schema IN ('bronze', 'silver', 'gold', 'app') AND table_type = 'BASE TABLE'
ORDER BY 1;"

docker exec subastas-analytics_42239a-subastas-db-1 psql -U subastas -d subastas -c "$COUNT_ROWS"   # local
docker exec subastas-analytics_42239a-subastas-db-1 psql "$NEON_URL" -c "$COUNT_ROWS"               # Neon
```

### 5. Point Airflow at Neon
In the root `.env`, with the old line kept as a fallback:

```bash
# AIRFLOW_CONN_SUBASTAS_DB='postgresql://subastas:<local-password>@subastas-db:5432/subastas'
AIRFLOW_CONN_SUBASTAS_DB='postgresql://neondb_owner:<password>@<neon-host>/subastas?sslmode=require&channel_binding=require'
```

Then `astro dev restart`, unpause the DAG and check that new rows reach Neon.

### 6. Point the app at Neon
In `dashboard/.Renviron`, with the app's user. The host is what's between `@` and `/` in the connection string:

```
SUBASTAS_DB_HOST=<neon-host>
SUBASTAS_DB_PORT=5432
SUBASTAS_DB_NAME=subastas
SUBASTAS_DB_USER=subastas_app
SUBASTAS_DB_PASSWORD=<subastas_app's password>
PGSSLMODE=require
```

Restart R and log in to check.

### Encrypted connections
`sslmode=require` makes the connection to Postgres encrypted, or fails if it can't be. Airflow and the app use the same Postgres driver, libpq, which accepts it in two ways:

- **In the connection string:** `...?sslmode=require`, as in Airflow's `.env`.
- **As an environment variable:** `PGSSLMODE=require`, as in the app's `.Renviron`, since `db.R` passes the connection values one by one and doesn't set it.

Without it, the default is `prefer`: encrypt if the server offers it, otherwise connect without encryption. Neon always encrypts, so `require` only makes sure it never connects without encryption.

To check the app's connection is encrypted, in R:

```r
Sys.getenv("PGSSLMODE")              # "require": .Renviron was read

Sys.setenv(PGSSLMODE = "disable")    # try without encryption
pool <- create_db_pool()             # fails: it opens a connection, and Neon only accepts encrypted ones
Sys.setenv(PGSSLMODE = "require")
```

### Setting the password of `subastas_app`
`create_app_role.sql` creates the role without a password, so it never ends up in git. It has to be set afterwards, as the owner:

1. Make a strong password, and save it in the password manager: `openssl rand -hex 24`. Hex only has `0-9` and `a-f`, so it never needs escaping in a connection string, and Neon rejects passwords that are too simple.
2. Set it with SQL, passing it to `psql` as a variable, so it isn't shown or saved in the shell history:

```bash
read -rs APP_PASSWORD && export APP_PASSWORD
echo "ALTER ROLE subastas_app PASSWORD :'pw';" | \
  docker run --rm -i -e NEON_URL -e APP_PASSWORD postgres:17 \
  sh -c 'psql "$NEON_URL" -v ON_ERROR_STOP=1 -v pw="$APP_PASSWORD"'
```

`:'pw'` is how `psql` puts a variable inside a statement as a quoted text.

Two other ways don't work:
- **The console's Reset password** only resets a password that already exists. A role created with SQL has none yet.
- **`\password subastas_app` in `psql`** hashes the password before sending it, and Neon only accepts plain-text passwords. The connection is encrypted, so the plain text doesn't travel in the clear.

## Moving Neon to Posit's region
The database was first created in AWS Frankfurt (`eu-central-1`). Posit's support confirmed that Posit Connect Cloud runs the apps in AWS `us-east-2` (Ohio), so every query of the app crossed the Atlantic. The database was moved to Ohio, next to the app. Why the database should be close to the app, rather than to the browser: "Where the database should be" in `13.performance.md`.

A Neon project's region can't be changed, so the move is a new project and a copy of everything. All the commands run in the `postgres:17` image, so `pg_dump` and `psql` don't need to be installed, and their version matches the server's.

### 1. Create the new project
Postgres 17, **AWS US East 2 (Ohio)**, database `subastas`, the same name as before, so only the host and the passwords change everywhere else.

Copy both projects' connection strings from **Connect**, with **Connection pooling** turned off: `pg_dump` and `pg_restore` need the direct host, the one without `-pooler`. Both strings must end in the database's real name, `/subastas`. With a name that doesn't exist, `pg_dump` fails and leaves an empty file, and the restore then has nothing to load.

```bash
read -rs OLD_DB && export OLD_DB   # old project
read -rs NEW_DB && export NEW_DB   # new project
```

### 2. Dump the old project
All the schemas (bronze, silver, gold and app), outside the repo, because the file contains the users' password hashes and their notes:

```bash
mkdir -p ~/neon_move && cd ~/neon_move
docker run --rm -e OLD_DB postgres:17 \
  sh -c 'pg_dump "$OLD_DB" --format=custom --no-owner --no-privileges' > subastas.dump
ls -lh subastas.dump    # several MB: a few bytes means the dump failed
```

- `--format=custom`: a compressed file that `pg_restore` reads.
- `--no-owner --no-privileges`: the old project's roles don't exist in the new one. The tables belong to the new project's owner, and the permissions come in step 4.

### 3. Restore into the new project

```bash
docker run --rm -i -e NEW_DB postgres:17 \
  sh -c 'pg_restore --no-owner --no-privileges --exit-on-error -d "$NEW_DB"' < subastas.dump
```

`--exit-on-error` stops at the first error, so a half-restored database doesn't look finished.

### 4. Create `subastas_app`
`pg_dump` doesn't copy roles. From the repo's root, as the new project's owner:

```bash
docker run --rm -i -e NEW_DB postgres:17 \
  sh -c 'psql "$NEW_DB" -v ON_ERROR_STOP=1' < include/sql/create_app_role.sql
```

Then set its password, as in "Setting the password of `subastas_app`" above, with `NEW_DB` instead of `NEON_URL`.

### 5. Check the copy
The same row counts on both projects:

```bash
COUNTS="SELECT 'bronze.auctions', count(*) FROM bronze.auctions
  UNION ALL SELECT 'silver.lots', count(*) FROM silver.lots
  UNION ALL SELECT 'gold.fact_lots', count(*) FROM gold.fact_lots
  UNION ALL SELECT 'app.users', count(*) FROM app.users
  UNION ALL SELECT 'app.lot_reviews', count(*) FROM app.lot_reviews"
for DB in OLD_DB NEW_DB; do
  echo "== $DB"
  docker run --rm -e "$DB" -e COUNTS="$COUNTS" postgres:17 sh -c "psql \"\$$DB\" -At -c \"\$COUNTS\""
done
```

And that `subastas_app` can read what the app needs, with its own connection string:

```bash
read -rs APP_DB && export APP_DB
docker run --rm -e APP_DB postgres:17 sh -c \
  'psql "$APP_DB" -At -c "SELECT count(*) FROM gold.app_lots" -c "SELECT count(*) FROM app.users"'
```

### 6. Point everything at the new project
Only the host and the passwords change:

| Where | What |
|---|---|
| Root `.env` | `AIRFLOW_CONN_SUBASTAS_DB`, as the owner. Then `astro dev restart` |
| `dashboard/.Renviron` | `SUBASTAS_DB_HOST` (the pooled host, with `-pooler`) and `SUBASTAS_DB_PASSWORD` |
| Posit Connect Cloud, the app's settings | The same two variables. Then restart the app |
| DBeaver | The connection's host and password |

### 7. Check, then delete the old project
1. The app locally: log in, open a lot, save a note and delete it.
2. The app on Posit: the same.
3. Airflow: the next run of the DAG writes to the new project.
4. Neon's dashboard: when nobody uses the app, the new project's compute goes to sleep.

Then delete the old project in Neon, and the dump in `~/neon_move/`.

## Deploying the app on Posit Connect Cloud
Posit Connect Cloud builds the app from the GitHub repo, not from the laptop. The R commands run in RStudio, with `dashboard.Rproj` open.

### 1. Get `renv.lock` in sync
Posit installs the packages listed in `renv.lock`, so it has to match what the app uses:

```r
renv::status()     # lists what's out of sync
renv::snapshot()   # records it in renv.lock
```

### 2. Generate `manifest.json`
It tells Posit which R version and which package versions to install:

```r
renv::install("rsconnect")
rsconnect::writeManifest(appFiles = c("app.R", "R/db.R", "R/auth.R"))
```

`appFiles` lists only the files the app needs, so `.Renviron` and `.Rprofile` are left out.

Whenever the app's packages change, run `renv::snapshot()` and `writeManifest()` again before merging, or Posit fails to install them. So it isn't forgotten, it's in the checklist of the PR template (`.github/pull_request_template.md`), which GitHub adds to every new PR.

### 3. Commit and push
Commit `dashboard/manifest.json` and `dashboard/renv.lock`, and merge them into `main`.

### 4. Publish on connect.posit.cloud
Publish → Shiny, repository `MiguelDonado/subastas_analytics`, branch `main`, primary file `dashboard/app.R`. Posit finds `manifest.json` next to it. The first build takes several minutes.

### 5. Set the environment variables in connect.posit.cloud
`.Renviron` isn't in git, so the app gets the database connection from the variables set in Posit, the same ones as in `.Renviron`:

```
SUBASTAS_DB_HOST      <neon-host>
SUBASTAS_DB_PORT      5432
SUBASTAS_DB_NAME      subastas
SUBASTAS_DB_USER      subastas_app
SUBASTAS_DB_PASSWORD  <subastas_app's password>
PGSSLMODE             require
```

Then open the app, log in and check that the lots show up.

## Stopping Airflow doesn't affect the database or the web application

The systemd service stops the containers with `astro dev stop`. That only stops the Airflow containers on my laptop. The database and the web application are still accessible, because they run in the cloud.

The problem would come from running everything locally. The most normal setup for that is to have everything in the same Compose project, so stopping Airflow would also shut down the database and the web application.

The workaround would be to put them in another Compose project, so that stopping or removing the Airflow project wouldn't affect them.

## Why a Pi needs extra work

By default, a home router blocks incoming connections from the internet. A browser can still receive webpages because those are responses to requests that started inside the network. A connection that starts outside the network has no such request, so the router drops it.

Letting a device in the network accept incoming connections normally means configuring port forwarding, dynamic DNS and TLS, and it doesn't work behind CGNAT. Cloudflare Tunnel avoids this configuration.

## How Cloudflare Tunnel works

`cloudflared` runs on the Pi and opens an outgoing connection to a Cloudflare server. The router allows it, because it starts inside the network, and the connection stays open.

Cloudflare publishes a domain. Traffic sent to that domain reaches Cloudflare, which forwards it to the Pi through the connection that is already open. It isn't a redirect: clients only talk to Cloudflare, and never connect to the Pi directly.

### Exposing a web application

```
Visitor's browser → Cloudflare → cloudflared (Pi) → Web application
```

Only the Pi needs `cloudflared`. Browsers speak HTTP, and an HTTP request says which domain it wants, so Cloudflare knows which tunnel to forward it to. Visitors don't have to install anything.

### Exposing a database

```
Airflow → cloudflared (laptop) → Cloudflare → cloudflared (Pi) → Database
```

Both sides need `cloudflared`. A database client speaks the Postgres protocol instead of HTTP, so it can't connect directly to the domain that Cloudflare publishes. `cloudflared` on the client wraps the traffic in a form that Cloudflare accepts, and the client connects to `cloudflared` as if it were a local database.

## Other possible setups

### Database and web application on the Pi

| Part | Where it runs |
|---|---|
| Airflow containers | My laptop |
| Database | Pi |
| Web application | Pi |

This was also relatively easy to set up, with `cloudflared` installed on both the laptop and the Pi:

- **On the laptop:** so that the Airflow containers can write to the database on the Pi.
- **On the Pi:** so that it can receive the traffic from Cloudflare.

Visitors would go to the domain published by Cloudflare, which would forward their traffic to the Pi.

```
Airflow (laptop) → cloudflared (laptop) → Cloudflare → cloudflared (Pi) → Database
Visitors → Cloudflare → cloudflared (Pi) → Web application → Database
```

### Only the web application on the Pi

| Part | Where it runs |
|---|---|
| Airflow containers | My laptop |
| Database | Neon |
| Web application | Pi |

`cloudflared` would only be installed on the Pi, so that visitors can reach the web application through the tunnel. The laptop wouldn't need it, because Airflow would connect directly to Neon.

```
Airflow (laptop) → Neon ← Web application (Pi) ← cloudflared (Pi) ← Cloudflare ← Visitors
```
