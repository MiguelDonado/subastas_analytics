# App design

Design of the final application: an R Shiny app to explore the auctioned properties, filter them, see them on a map and mark the ones of interest.

## Layout
- **Left sidebar:** filters.
- **Main area, top:** map with the catastral references of the results.
- **Main area, bottom:** table with the results and their main characteristics, one row per lot.

Clicking a row in the table shows all of the lot's catastral references on the map, zoomed to fit them. Clicking a point on the map highlights the row of its lot in the table.

Clicking a point selects its lot's row and moves the table to the page where that row is, however the table is sorted. It also opens a popup with that catastral reference's data (use, class, surface, crop) and a link to Google Maps.

## Map
QGIS is a desktop application and can't be embedded in a Shiny page, so the app uses a web map library: the R package **leaflet**.
- It has a built-in control to switch between layers.
- It can zoom the map to fit an area (`fitBounds`) without redrawing it, which is what clicking a row needs.
- It reports marker clicks back to Shiny (`input$map_marker_click`), so the map can also select rows in the table.

QGIS is still useful outside the app, to explore the data or prepare layers.

### Layers
Base maps (one at a time):
- **OpenStreetMap**
- **Aerial photo Esri:** Esri World Imagery.
- **Aerial photo PNOA:** the IGN's official aerial photo of Spain.

Overlays (can be turned on over any base map, off at start):
- **Catastro parcels:** parcel outlines and numbers. Only drawn when zoomed in close.
- **Hydrography:** rivers and water bodies, from the IGN.

### Map services instead of downloaded files
All layers come from public map services, which send ready-made images of the area on screen. Downloading the data (e.g. the shapefiles of all the Catastro of Spain) is only worth it when we need to compute something with it, such as the distance from a parcel to a river. To just look at it, the services are better:
- **Size:** the Catastro of Spain is tens of millions of parcels, tens of GB split into one download per municipio. The Basque Country and Navarra aren't even included, they have their own Catastro.
- **The browser can't draw it:** leaflet can't handle millions of shapes. Showing our own copy would need our own map server, which is what the Catastro and the IGN already provide.
- **Always up to date:** a download gets old and has to be downloaded again.

The cost is that the map depends on those services being online.

If one day we need the exact shape of the auctioned parcels, the Catastro can return the shape of a single catastral reference. Fetching only the auctioned ones is a few thousand shapes, not all of Spain.

### Points, not shapes
The database stores one point per catastral reference (`latitude` and `longitude`, the centre of the parcel that Goolzoom returns), not its outline/shape. So the map draws a marker per reference. To see the outline/shape, zoom in with the **Catastro parcels** layer on: it draws the parcel edges, and the marker sits inside its parcel.

### Markers for every result
The map shows a marker for every catastral reference of the filtered lots, even when there are many. It shows which areas have results, so it helps to narrow the search, instead of showing an empty map until a row is clicked. Clicking a row highlights the markers of that lot and zooms into them.

### addProviderTiles or addTiles
- **`addProviderTiles("Esri.WorldImagery")`:** for services already in leaflet's list of known providers. Just the name, leaflet knows the URL.
- **`addTiles(urlTemplate = ...)`:** for anything not in that list, like the PNOA. We have to write the URL ourselves, with `{z}`, `{x}` and `{y}` where leaflet fills in the zoom and the position of each tile.
- **`addWMSTiles`:** for WMS services, like the Catastro and the hydrography. The layer names come from the service's own description, which you get by opening its URL with `?service=WMS&request=GetCapabilities`.

Google Maps isn't an option: it's not in the list, and loading its tiles directly breaks Google's terms.

### PNOA or Esri
Esri is the simplest, but the PNOA is probably better for judging rural parcels:
- **Sharper and dated:** the PNOA is 15–25 cm per pixel and is flown again every 2–3 years. Esri mixes sources, often less sharp in rural Spain, and doesn't say how old each image is.
- **Matches the Catastro:** the Catastro draws its parcels over the PNOA, so the outlines match the fences and field edges. Over Esri they can be off by a few metres.
- **Only Spain:** outside Spain the PNOA is blank, which doesn't matter here.

## One table row = one lot
Prices are stored per **lot**, but coordinates and surface are stored per **catastral reference**, and one lot can have several. So the table displays the view `gold.app_lots`, where each row is a lot, with:
- total surface (sum of its catastral references)
- starting price
- price per m²
- municipio and province
- use and class
- qualification (the most common among its catastral references)

The table only contains the last auction of each lot, which are the rows of the view with `is_latest = true`. A lot that is auctioned again keeps the same catastral references, so the view recognises its earlier auctions by that list of catastral references. Earlier auctions aren't shown because they aren't relevant when deciding whether to buy a property, but they can still be queried directly in the gold tables.

The map can't use this view, because it needs one point per catastral reference. It reads the coordinates from `gold.dim_catastral_references`, through `gold.lots_catastral_references_bridge`. The price and surface filters work on the lot-level values of the table.

Each row also links to the BOE announcement (`announcement_url`).

Rows are sorted by offer deadline, then announcement, then lot number, so the next deadline comes first and the lots of one announcement stay together.

## Filters
The filters are applied when clicking **Buscar**. An empty filter lets every lot through.

- **Provincia:** multi-select box; empty means all provinces.
- **Municipio:** multi-select box, to stay in one or a few municipios once the province is narrowed down. It only offers the municipios of the selected provinces (all of them if none is selected), and keeps the ones already picked that are still in the list.
- **Clase:** multi-select box, e.g. to see only the urbanos and look for a good opportunity. A lot's class is the most common among its catastral references, so a lot with one urbano and two rústicos counts as rústico.
- **Precio máximo:** only a maximum; a minimum price doesn't help to decide.
- **Superficie mínima:** only a minimum; a maximum surface doesn't help to decide.
- **Anuncio (BOE):** to find one lot directly. Filter by its BOE reference, then look for the row with its lot number (Nº lote). Part of the BOE reference is enough, e.g. `12345` finds `BOE-B-2026-12345`. There's no lot number filter, because an announcement only has a few lots. The other filters still apply, so turn off "Solo subastas activas" or clear the province if the lot doesn't appear.
- **Estado:** multi-select box with the user's status of each lot: Sin revisar, Interesado, Descartado. For the weekly check, "Sin revisar" shows the lots you haven't decided on yet, new or not. More in `docs/11.reviews.md`.
- **Solo subastas activas:** a switch, on by default, that hides auctions whose offer deadline has passed. Past auctions are mostly useful for analysis, not for deciding. It's done in R, not in the view: "active" depends on today's date, and the app reads the view only once when it starts, so the view's value would get stale. It's only a filter, not a table column, because the Plazo ofertas column is already obvious.

Not filters, only shown in the table:
- **Cultivo:** secondary information and not always accurate, not important enough to hide a property. It's shown to confirm what kind of trees an interesting property has.
- **Price per m²:** not needed for now; price and surface already narrow the list.

## Marking lots of interest
Each user can mark each lot with a **status**, Interesado or Descartado (none means not reviewed yet), and write a **note** on it. They're chosen in the note card of the sidebar, shown in the "Estado" and "Nota" columns of the table, and the "Estado" filter uses the status. How it's built is in `docs/11.reviews.md`.

They're data the user enters, while bronze, silver and gold are written by the pipeline and can be rebuilt. So they live in their own schema, outside the medallion layers:

```
app.lot_reviews (user_id, boe_ref, lot_number, notes, status, updated_at)
```

The lot is identified by **`boe_ref` + `lot_number`**, not `lot_id`. `lot_id` is generated automatically, so rebuilding silver gives every lot a new number and the notes would point to the wrong lots. The BOE reference and lot number never change.

### Each user has their own notes
The app is used by a known group of people, so each one logs in (shinymanager) and keeps their own notes and statuses: what one person marks isn't seen by the others. That's why the table has `user_id`, and its primary key is `user_id` + `boe_ref` + `lot_number`.

The notes and statuses depend on who is logged in, so they can't go in `gold.app_lots`: the app reads the user's ones and joins them to the lots in R.

### A re-auctioned lot comes back without its note and status
When a lot is auctioned again, it comes in a new announcement, with a new `boe_ref`. Its note and status were saved under the old one, so the new auction shows up as not reviewed. This keeps it simple, and a new auction usually has a lower price, so a fresh look can make sense.

## What this means for gold
The app needs a table with one row per lot holding everything it shows and filters on. Gold can still be a star schema for analysis, and the app's table reads from a view built on it, `gold.app_lots`.

The notes from `app.lot_reviews` don't go in the view, because they depend on the user who is logged in (see "Each user has their own notes").
