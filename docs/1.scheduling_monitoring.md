# Scheduling and monitoring

How the weekly pipeline gets scheduled, why Airflow is only running for about two hours a week, and how I find out when something goes wrong.

## Why Airflow only runs once a week

BOE data only needs loading once a week, so keeping Airflow running all the time would use RAM for nothing. This project's Airflow containers use about 1.1 GiB when running, on a laptop with 15 GiB that also runs `cgm-analytics`, which has to stay on because it fetches data hourly.

So a cron job starts Airflow every Monday, gives it two hours to finish, and stops it again. Stopping the containers frees their RAM, and the data stays in Docker volumes.

This means scheduling has two layers:

- **Cron** decides when the containers are running. It doesn't trigger the DAG.
- **Airflow** decides what runs and when it's due.

## Weekly flow

| When | What happens |
|---|---|
| Monday 00:00 UTC | The DAG's scheduled time passes. Airflow is off, so nothing runs yet. |
| Monday 10:30 local | Cron runs `scripts/weekly_airflow.sh`, which starts Airflow. |
| Right after the start | Airflow sees the missed Monday and starts that run (`catchup=True`). |
| Monday 12:30 local | The script stops Airflow. |

## Why the DAG is scheduled at 00:00 UTC

The DAG is scheduled at Monday 00:00 UTC on purpose, so that it comes before the cron job. Every run is technically a catch-up, and it starts as soon as Airflow is up.

This is safer than scheduling the DAG inside the cron window. Cron runs on local time and Airflow on UTC, so the two would have to be kept in sync. This way, changing the time of the cron job or the clocks changing doesn't require any change in the DAG, as long as cron stays on Monday.

## Cron job

Installed with `crontab -e`:

```cron
30 10 * * 1 /home/miguel/6.Projects/subastas_analytics/scripts/weekly_airflow.sh >> /home/miguel/6.Projects/subastas_analytics/logs/weekly_airflow.log 2>&1
```

- **Schedule:** every Monday at 10:30, in the laptop's local time.
- **Logs:** the script's output and errors are appended to `logs/weekly_airflow.log`, so the file keeps every week's output. The script adds a timestamp to each line. The `logs/` folder is gitignored, but has to exist for the job to write there.

## Failure alerts

With two scheduling layers, there is more that can go wrong, so the pipeline relies on [healthchecks.io](https://healthchecks.io) and follows the logic of "no news is bad news". Its check waits for a ping from the DAG, so it also notices when Airflow never ran. An email sent by Airflow couldn't cover that, because Airflow has to be running to send it.

The DAG sends two pings:

- **Success:** `ping_success` is the last task and only runs if bronze, silver and gold all succeeded.
- **Failure:** `_ping_failure` calls the `/fail` URL when a task fails on its last retry. A failure that a retry fixes sends no alert.

| What happens | Result |
|---|---|
| The run succeeds | Success ping, no email |
| A task fails on its last retry | `/fail` ping, immediate email |
| The laptop is off, or Airflow doesn't start | No ping, email on Tuesday around 10:30 local |

The check is set up on healthchecks.io with these values:

- **Schedule: `30 10 * * 1`, in local time.** The same schedule as the cron job, so it has to be updated if the cron job moves.
- **Grace time: 1 day.** How long to wait after the scheduled time before alerting.

The `/fail` ping ignores the schedule and the grace time. If one run fails and another succeeds in the same window, the check ends up as OK, but the `/fail` email has already been sent.

The email only says that something went wrong, so the cause has to be found in the Airflow UI.

## Logs

`logging.getLogger(__name__)` doesn't create a log file. It only creates a logger named after the module, such as `subastas_analytics.loaders.silver`. When a task is running, Airflow writes that logger's messages, and anything sent with `print`, to the log of that task. So the `REJECTED` and `FAILED` messages from `load_silver` are in the log of the silver task that called it.

Each attempt of each task has its own file:

```
/usr/local/airflow/logs/dag_id=subastas_pipeline/run_id=<run>/task_id=<task>/attempt=<n>.log
```

- **Where to read them:** in the Airflow UI.
- **Where they are stored:** in a Docker volume, not in the project's `logs/` folder.

### Logs explain problems, they don't detect them

You don't need to read the logs to notice that something went wrong: healthchecks.io emails you (see [Failure alerts](#failure-alerts)). You only open the logs after an alert, to find out why, and the log of the failed task is where you'd look first anyway. So the task logs are enough.

### Who configures logging

- **Modules only create a logger and log.** Each module does `logger = logging.getLogger(__name__)` and calls `logger.warning(...)` and so on. They never set levels or handlers.
- **The application configures logging once, on the root logger.**
  - **Airflow** does it for every task, at level `INFO`, so messages end up in the task log in the UI.
  - **Scripts** (`scripts/try_*.py`) don't configure anything, so only `WARNING` and above get through, printed to stderr. Add `logging.basicConfig(level=logging.INFO)` to see `INFO` too.
- **How the messages get there:** a module's logger has no level or handlers of its own. Python takes the level from the nearest ancestor that has one, usually the root logger. It also passes every message up the hierarchy to the root logger's handlers (`propagate=True` by default).

## Known limitations

- **Laptop off or asleep at 10:30 on Monday:** cron skips that week and doesn't run it later. The next Monday's start catches up on both weeks, so the data arrives a week late but nothing is lost. This trade-off was accepted to keep cron instead of a systemd timer with `Persistent=true`.
