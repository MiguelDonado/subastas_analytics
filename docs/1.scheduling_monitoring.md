# Scheduling and monitoring

How the weekly pipeline gets scheduled, why Airflow is only running for about two hours a week, and how I find out when something goes wrong.

## Why Airflow only runs once a week

BOE data only needs loading once a week, so keeping Airflow running all the time would use RAM for nothing. This project's Airflow containers use about 1.1 GiB when running, on a laptop with 15 GiB that also runs `cgm-analytics`, which has to stay on because it fetches data hourly.

So a systemd timer starts Airflow every Monday, gives it two hours to finish, and stops it again. Stopping the containers frees their RAM, and the data stays in Docker volumes.

This means scheduling has two layers:

- **The systemd timer** decides when the containers are running. It doesn't trigger the DAG.
- **Airflow** decides what runs and when it's due.

## Weekly flow

| When | What happens |
|---|---|
| Monday 00:00 UTC | The DAG's scheduled time passes. Airflow is off, so nothing runs yet. |
| Monday 10:30 local | The timer runs `subastas-airflow.service`, which waits 2 minutes and starts Airflow. |
| Right after the start | Airflow sees the missed Monday and starts that run (`catchup=True`). |
| 2 hours after the start | The service stops Airflow. |

## Why the DAG is scheduled at 00:00 UTC

The DAG is scheduled at Monday 00:00 UTC on purpose, so that it comes before the timer. Every run is technically a catch-up, and it starts as soon as Airflow is up.

This is safer than scheduling the DAG inside the timer's window. The timer runs on local time and Airflow on UTC, so the two would have to be kept in sync. This way, changing the time of the timer or the clocks changing doesn't require any change in the DAG, as long as the timer stays on Monday.

## Systemd timer

The two files are in `systemd/`, and their comments explain each line:

- `subastas-airflow.timer` says when to run.
- `subastas-airflow.service` says what to run: start Airflow, wait 2 hours, stop Airflow.

To install them, or to apply a change to them:

```bash
sudo cp systemd/subastas-airflow.* /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now subastas-airflow.timer
```

- **Schedule:** every Monday at 10:30, in the laptop's local time.
- **Laptop off or asleep at 10:30 on Monday:** `Persistent=true` makes the timer run at the next boot or wake. It records when the service started, not when it finished, so a shutdown during the window isn't run again until the next Monday.
- **Logs:** see them with `journalctl -u subastas-airflow.service`. Each line has a timestamp, and the logs survive reboots. The oldest ones are removed when the journal reaches its size limit.

## Systemd: Requires, Wants and After

- `Wants=X`: "Start X too. If X fails, I'll run anyway."
- `Requires=X`: "Start X too. If X fails, I shouldn't run."
- `After=X`: "If X is starting, wait until it's finished before I start, whether it worked or failed." It doesn't start X by itself.

Example: imagine you're making breakfast.

- `Wants=toast`: put the toast on, but if the toaster breaks, breakfast goes ahead without it.
- `Requires=coffee`: make coffee, and if the coffee machine breaks, there's no breakfast.
- `After=coffee`: don't sit down until the coffee is ready.

`Wants` and `Requires` say what gets started. `After` says in what order. That's why they're usually used together.

`After` only sets the order, so it never blocks the service forever:

| What happens to the other service | What this service does with `Wants` + `After` |
|---|---|
| Starts fine | Waits for it, then starts |
| Tries to start and fails | Waits for the failure, then starts anyway |
| Isn't being started at all | Doesn't wait, starts right away |

In `systemd/subastas-airflow.service`:

- Docker uses `Requires` and `After`: start Docker, wait until it's ready, and don't run if it fails.
- Network uses `Wants` and `After`: wait for the network, but if it isn't there after a while, start anyway. You'll get an alert if the run then fails.

## Failure alerts

With two scheduling layers, there is more that can go wrong, so the pipeline relies on [healthchecks.io](https://healthchecks.io) and follows the logic of "no news is bad news". Its check waits for a ping from the DAG, so it also notices when Airflow never ran. An email sent by Airflow couldn't cover that, because Airflow has to be running to send it.

The DAG sends two pings:

- **Success:** `ping_success` is the last task and only runs if bronze, silver and gold all succeeded.
- **Failure:** `_on_task_ping_failure` calls the `/fail` URL when a task fails on its last retry. A failure that a retry fixes sends no alert, except when announcements had already failed before an outage stopped the silver task (S33 in `6.failure_modes.md`).

| What happens | Result |
|---|---|
| The run succeeds | Success ping, no email |
| A task fails on its last retry | `/fail` ping, immediate email |
| The laptop is off, or Airflow doesn't start | No ping, email on Tuesday around 10:30 local |

The check is set up on healthchecks.io with these values:

- **Schedule: `30 10 * * 1`, in local time.** The same schedule as the timer, so it has to be updated if the timer moves.
- **Grace time: 1 day.** How long to wait after the scheduled time before alerting.

The `/fail` ping ignores the schedule and the grace time. If one run fails and another succeeds in the same window, the check ends up as OK, but the `/fail` email has already been sent.

The email only says that something went wrong, so the cause has to be found in the Airflow UI.

## Running a missed or failed week

Each run fetches the 7 days before its own Monday (its `logical_date`), not the 7 days before today. So a week can run late and still fetch the right days. For example, the run of Monday 2 November fetches 26 October to 1 November, even if it runs on 20 November.

| What happened | What to do | Days fetched |
|---|---|---|
| The laptop was off on Monday, so the run doesn't exist | Nothing. The timer starts Airflow at the next boot, and Airflow creates one run for each missed week and runs them one at a time | Each run fetches its own week |
| The run failed | Fix the cause, start Airflow if it's stopped, and clear the failed run with "Only failed" | The same week as before |

Don't use the Trigger button for this. It creates a new run with a new date, so it fetches the 7 days before that date, and the failed or missed week still isn't covered.

To start Airflow by hand, and stop it once the runs have finished in the UI:

```bash
cd /home/miguel/6.Projects/subastas_analytics
astro dev start --no-browser
astro dev stop
```

### Why 7 days is enough

Fetching more days as a safety margin isn't needed. A failed run stays failed and alerts, and clearing it fetches the same week. A run that never happened is created by `catchup=True`, and healthchecks.io alerts if the laptop stays off. Each run goes from the previous Monday to Sunday, so there are no gaps between weeks.

## Logs

`logging.getLogger(__name__)` doesn't create a log file. It only creates a logger named after the module, such as `subastas_analytics.loaders.silver`. When a task is running, Airflow writes that logger's messages, and anything sent with `print`, to the log of that task. So the messages from `load_silver` (`LOADED`, `REJECTED`, `STOPPED`, `FAILED`) are in the log of the silver task that called it.

Each attempt of each task has its own file:

```
/usr/local/airflow/logs/dag_id=subastas_pipeline/run_id=<run>/task_id=<task>/attempt=<n>.log
```

- **Where to read them:** in the Airflow UI.
- **Where they are stored:** in a Docker volume, not in the project's `logs/` folder.

### Silver: every announcement ends with one log line

`load_silver()` first logs how many announcements are pending (`N pending announcements in bronze`). Then every announcement ends in exactly one of these outcomes, and each one writes a log line with its `boe_ref`. All of them are logged from `load_silver()` itself, so the whole run can be followed there in order:

| Outcome | Why | Log line | What happens next |
|---|---|---|---|
| **Loaded** | The auction has a held date and at least one valid lot | `INFO LOADED <boe_ref>` | Committed, carries on with the next one |
| **Failed** | The announcement has a problem: no held date, no valid lots (no starting price, no catastral references, or an invalid one), Claude refused it, an error... | `ERROR FAILED <boe_ref>: ...` | Saved in `silver.failed_announcements` with the reason, so it isn't sent to Claude again. The rest carry on, and the task fails at the end and alerts |
| **Stopped** | An outside service failed: Claude or Goolzoom is down, rate limited or timing out. It isn't the announcement's fault | `ERROR STOPPED at <boe_ref>: ...`, followed by Airflow's traceback | Rolled back. The rest aren't tried, the task fails and Airflow retries it |

The lines below an announcement explain the details, and they come from the helpers:

- `REJECTED <boe_ref> lot <n>: ...` from `_store_auction()`, for each invalid lot.
- `REJECTED <boe_ref> lot <n>: reference ...` from `_get_reference_id()`, for each invalid reference.

A lot with any invalid reference isn't stored, because its surface would be wrong. The rest of the announcement is.

So searching the silver task log for `STOPPED` means "check the service", and `FAILED` means "check that announcement".

A FAILED announcement doesn't stop the others, but it fails the task and alerts you. See [What a FAILED announcement does to the run](6.failure_modes.md#what-a-failed-announcement-does-to-the-run).

### Logs explain problems, they don't detect them

You don't need to read the logs to notice that something went wrong: healthchecks.io emails you (see [Failure alerts](#failure-alerts)). You only open the logs after an alert, to find out why, and the log of the failed task is where you'd look first anyway. So the task logs are enough.

### Who configures logging

- **Modules only create a logger and log.** Each module does `logger = logging.getLogger(__name__)` and calls `logger.warning(...)` and so on. They never set levels or handlers.
- **The application configures logging once, on the root logger.**
  - **Airflow** does it for every task, at level `INFO`, so messages end up in the task log in the UI.
  - **Scripts** (`scripts/try_*.py`) don't configure anything, so only `WARNING` and above get through, printed to stderr. Add `logging.basicConfig(level=logging.INFO)` to see `INFO` too.
- **How the messages get there:** a module's logger has no level or handlers of its own. Python takes the level from the nearest ancestor that has one, usually the root logger. It also passes every message up the hierarchy to the root logger's handlers (`propagate=True` by default).

## Known limitations

- **Power cut during the weekly window:** the containers should only run during the window, so they use `restart: "no"` in `docker-compose.override.yml`. Astro sets them to `unless-stopped`, so without this they would start on boot and stay up until the next `astro dev stop`. There is a trade-off: with `unless-stopped`, a run cut off by a power cut would carry on by itself on boot. We still prefer `"no"`, so the containers don't stay running in the background during the whole week without us knowing. The cut-off run stays paused until Airflow next starts, and healthchecks.io alerts us because the success ping never arrives.
